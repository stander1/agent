## 2. 原始验收与口径缺陷

原始脚本给出 `11/13`：

```text
fault_injection_is_observed_not_assumed:
  native=10/12
  managed=11/12

safe_and_negated_outputs_have_no_false_positive:
  safe=3/4
```

逐行检查确认，失败都来自 `structured_negated_history`：

- Native 两次均只输出 `service.capacity=50`，没有复述“不要使用 20”；
- Managed 第一次输出完整否定句，并被安全放行；
- Managed 第二次只输出 `service.capacity=50`，同样被安全放行。

旧验收器把“没有复述否定句”同时算成“故障未注入”和“安全场景失败”。这是验收口径
缺陷，不是运行时守卫失败。仅输出活动值 50 没有采用历史值，也没有触发守卫，属于安全
退化输出。

修正后的口径为：

1. 危险旧值故障必须逐次真实出现，才能计入修复或阻断成功；
2. 否定旧值场景至少需要一条 Managed 输出真实包含否定句；
3. 其他重复样本若只输出活动值、没有正向旧值且未触发守卫，则记为安全退化；
4. 任何正向旧值逃逸或安全输出被修复/阻断，仍判为失败。

对原始不可变证据重新验算后为 `14/14`，没有修改 Provider 输出或 trace。

## 3. 逐场景结果

| 场景 | 重复数 | Native | Managed | 下游结果 |
|---|---:|---|---|---|
| 正确当前值 | 2 | 安全输出 | 安全放行 | 当前值 50 |
| 仅历史值 | 2 | 旧值泄漏 | `rule_repaired` | 旧值 20 被修复为 50 |
| 新旧混合 | 2 | 混合值泄漏 | `rule_repaired` | 历史值归一为 50 |
| 明确否定旧值 | 2 | 两次均省略否定句 | 1 条真实否定安全放行，1 条安全退化 | 无正向旧值 |
| 无关字段同值 | 2 | 旧容量泄漏 | `rule_repaired` | 容量改为 50，`ticket_count=20` 保留 |

## 4. Token 与延迟

| 组别 | LLM 调用 | Prompt Token | Completion Token | 总 Token | LLM 时间 | 总时间 | 重试 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Native | 12 | 1,192 | 1,910 | 3,102 | 68.404 s | 68.476 s | 0 |
| Managed | 12 | 10,858 | 6,488 | 17,346 | 143.899 s | 149.622 s | 0 |

Provider 可见文本很短：

```text
Native raw output: 358 chars total, 29.8 chars average
Managed raw output: 391 chars total, 32.6 chars average
```

因此本实验中 Managed 的 Token 和延迟显著高于 Native。主要原因是：

- 每个任务只要求一行输出，原生消息极短；
- Managed 仍注入结构化活动值、修订守卫、状态视图和协作控制信息；
- Provider 对更长上下文产生了更多计费 completion/reasoning Token。

该结果不支持“短消息故障探针能够降低 Token”这一说法。v5.14a 的有效结论仅限于真实
AutoGen 消息链中的旧事实传播防护；低开销结论仍应使用正常长度、连续协作任务的公平
实验评估。

## 5. 可确认结论

可以确认：

1. 真实 Provider 产生的结构化历史值可在离开发出 Agent 前被精确修复；
2. 无法证明可安全替换的旧版非结构化冲突会被保守阻断；
3. 修复后的消息才进入下游 AutoGen Agent；
4. 明确否定旧值不会被当成正向采用；
5. 相同数字但不同语义键的字段不会被连带修改；
6. 修复和阻断均产生补偿审计事件。

不能据此确认：

1. AgentLite 在所有消息长度下都降低 Token；
2. AgentLite 在本故障矩阵中降低延迟；
3. 这 12 个短输出样本足以代表完整用户任务的交付质量。

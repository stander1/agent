# v5.14d 最终成果解析、硬约束守卫与路由状态净化

## 1. 证据来源

本阶段只处理 v5.14c 真实 openEuler 预检归档
`v5.14b-fair-cost-quality-preflight-v514c-20260724-215333.tar.gz` 暴露的问题。
原始结果为：

- Native Provider Token：`96,739`
- Managed Provider Token：`94,327`
- Provider Token 降幅：`2.49%`
- Native 双盲质量均分：`8.8333`
- Managed 双盲质量均分：`6.8333`
- Managed 端到端协作 Token：`28,349`
- Native 对照协作 Token：`71,931`
- 端到端协作 Token 降幅：`60.59%`

这说明通信改写已经有效，但最终成果识别和终止控制仍会额外调用模型或选错交付正文。

## 2. 根因

### 2.1 完整成果缺少结束标记后继续运行

A3 第一轮 Reviewer 已产生完整、预算合规的最终方案，但没有在最后一行输出
`FINAL_ANSWER_READY`。旧终止器因此继续执行第二轮
Planner、Writer、Reviewer，共增加 `19,569` Provider Token 和 `134,222 ms`
模型等待时间。第二轮反而把总预算上界写成 `3,800` 元，导致质量下降。

### 2.2 批准说明被当成最终成果

B1 Writer 已生成 `2,445` 字完整审计报告。Reviewer 只输出约 `207` 字的验收和批准
说明，旧实验代码直接把最后一条消息作为最终答案，最终交付缩成 `187` 字，双盲评分
因此降到 1 分。

### 2.3 数字硬约束只做结构验收

旧 Final Delivery Guard 能阻止审查意见伪装成交付物，但不能校验“总预算不得超过
某值”与结果总计之间的矛盾，因此 A3 第二轮的 `3,800 > 3,000` 未被拦截。

### 2.4 路由对象进入状态池

v5.14c 的路由过滤没有覆盖 `CancellationToken` 和混合业务文本中的控制对象。
归档的 120 个物理状态中有 42 个包含 `DefaultTopicId`、`AgentId` 或
`CancellationToken`，约占 35%。此外，监控快照只处理 `state_written`，没有合并
`state_reused`，导致实际复用次数在报告中显示为 0。

## 3. 通用修复

### 3.1 最终成果解析

`ReviewerFinalTextTermination` 现在保留最近一份非 Reviewer 候选成果，并区分三种结果：

- `reviewer_artifact`：Reviewer 正常输出完整成果和精确结束标记；
- `reviewer_marker_repaired`：Reviewer 已输出具有明确交付边界的完整成果，但漏写结束
  标记；运行时只补标记，不再调用模型；
- `prior_artifact_approved`：Reviewer 只验收或批准前序成果；最终交付引用前序完整成果，
  不把批准说明当成正文。

解析依据是消息来源、交付边界、审查语义和成果谱系，不依赖 Planner、Writer 的固定
名称。Reviewer 名称仍由终止条件配置提供。

普通开发者实验输出新增：

- `final_artifact_origin_source`
- `final_resolution_kind`

原始消息列表继续完整保留，最终答案只是对已有消息的确定性解析，不修改 Provider
原文。

### 3.2 硬约束守卫

Final Delivery Guard 新增规则优先的数值上限校验。当前覆盖通用预算上限表达，例如
“以内”“不得超过”“at most”“maximum”。只有请求或历史上下文明确给出预算上限，
且结果中的总计、合计或总费用超过该上限时才触发
`numeric_upper_bound_violation`。

这不是 Question A 特判，不包含目的地、任务编号或旅游景点名称。没有明确上限的任务
不会触发该规则。

### 3.3 路由状态净化

AutoGen 状态准入前先构造语义正文：

1. 删除 `DefaultTopicId(...)`、`AgentId(...)`、`CancellationToken` 和纯 UUID 路由
   前缀；
2. 仅剩控制对象时记录 `autogen_routing_metadata_filtered`，不写入 StatePool；
3. 同一消息同时包含业务正文与路由对象时，只保留业务正文；
4. 工具调用和工具结果仍属于业务状态，不被过滤。

### 3.4 复用统计修复

监控快照同时处理 `state_written` 和 `state_reused`。相同 `state_id` 的复用事件更新
已有状态行，不增加物理状态数，并保留最新 `dedup_reuse_count`。

## 4. 离线回放结论

使用 v5.14c 归档中的真实消息回放新解析器：

- A3：解析为 `reviewer_marker_repaired`，保留第一轮 Reviewer 的 `2,232` 字完整成果；
- B1：解析为 `prior_artifact_approved`，恢复前序 Writer 的 `2,465` 字完整成果；
- A3 第二轮 3 次调用不会发生。

按原日志扣除 A3 第二轮的 `19,569` Token，Managed Provider Token 的反事实值为
`74,758`，相对 Native `96,739` 的降幅约 `22.72%`。该数值只用于解释根因和估计修复
影响，不能替代新的真实 Provider 实验。

## 5. 公平边界

```text
不修改 Question A/B 题目、领域提示词或双盲评分标准；
不限制 completion 长度；
不减少预注册 max_turns；
缺标记修复只接受已有完整成果，不调用 LLM 补写正文；
批准说明只能提升已经存在且通过守卫的前序成果；
预算规则只有在上下文存在明确上限时生效；
原始 Provider 输出、调用用量和消息序列继续完整保存。
```

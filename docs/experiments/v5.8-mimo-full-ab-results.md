## 5. 变化解释

### 5.1 runtime_lite 仍然显著优于 baseline

v5.8 A+B 合计中，runtime_lite 相比 baseline_text：

1. provider 总 token 降低 94.34%。
2. 端到端协作 token 降低 97.65%。
3. 总延迟降低 19.85%。
4. fallback_count 仍为 0。
5. A10 / B10 最终交付 schema 均完整。

这说明 v5.1-v5.8 新增的治理机制没有破坏原本的低开销协作优势。

### 5.2 与 v4.2 相比，runtime_lite 的内部协作 token 上升

`end_to_end_collaboration_tokens` 从 116,161 增加到 139,536，主要原因是：

1. SHPEnvelope 现在包含 header/control/metrics，而不是旧的轻量 JSON。
2. v5.5 加入 route_decision、communication_gate、control_budget 等可审计控制字段。
3. direct_text_tokens 从 24,416 增加到 45,662，说明新增开销主要发生在 SHP 控制包本身。

这是一种“用少量协议元数据换可解释性与鲁棒性”的开销。虽然内部协作 token 上升 20.12%，但相比 baseline 仍下降 97.65%。

### 5.3 provider token 只小幅上升

runtime_lite 的 `llm_total_tokens` 从 235,011 增到 241,722，上升 2.86%。这说明新增控制字段没有明显进入大模型 prompt 的长上下文路径，主要停留在 SHP 交接和 metrics 侧。

### 5.4 延迟反而下降

runtime_lite 延迟从 1,734,706ms 降到 1,506,463ms，下降 13.16%。这不能完全归因于代码优化，因为 baseline 也快了 17.24%，说明本轮 MiMo 网络/服务端状态比 v4.2 更好。

但至少可以确认：v5.1-v5.8 新增机制没有导致延迟恶化。

### 5.5 新增治理指标开始可见

v5.8 新增了以前没有的运行时治理证据：

1. `control_decision_count=100`：每次 runtime_lite Agent handoff 都经过控制决策。
2. `route_override_count=20`：每组 10 次路由改写，A+B 共 20 次。
3. `communication_gate_block_count=0`：本轮没有被阻断。
4. `communication_gate_degraded_count=0`：本轮没有降级交接。
5. `read_lease_acquire_count=260`：Read Lease 现在覆盖 Progressive Access 与 Prompt View。
6. `raw_access_count=0`、`access_escalation_count=0`：本轮默认 summary-first，没有把 raw 冷数据塞回 prompt。

## 6. 结论

本轮 v5.8 A/B 的关键变化是：

1. 低开销优势仍成立：runtime_lite 相比 baseline 仍节省 94.34% provider token。
2. 系统更“硬”：SHP 协议、路由、门控、租约等审计要求现在能被指标看见。
3. 内部协议开销上升：相比 v4.2，runtime_lite 的 direct_text_tokens 明显增加，这是更完整 SHPEnvelope 和控制 metrics 带来的。
4. 成本没有失控：虽然内部协作 token 增加，provider token 只增加 2.86%，且相比 baseline 仍大幅下降。
5. 没有质量退化信号：A10 为 16/16，B10 为 12/12，fallback_count 为 0。

因此，v5.8 相比 v4.2 的定位变化是：

> v4.2 更像“低开销效果证明”；v5.8 更像“可审计、可解释、具备运行时治理的低开销原型”。它牺牲了少量 SHP 控制包 token，换来了协议完整性、路由证据、读租约证据和冷访问治理证据。

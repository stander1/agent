# v5.13z 错误记忆采用修复闭环

## 问题定位

v5.13y 的真实 AutoGen 实验已经证明系统能够识别 `wrong` 和 `mixed`
记忆采用，但原链路在 Agent 输出完成后才执行归因。对
`on_messages_stream()` 而言，原消息已经先进入下游，随后系统才写审计事件。
因此旧事实仍可能污染后续 Agent。

## 修复策略

新增框架无关的 `memory_adoption_guard`，并在 AutoGen 完整消息出流前执行：

1. 使用 CCF v2 的语义键、当前有效值、历史值和命中输出片段判定冲突；
2. 仅在历史标量位于已匹配片段且可精确替换时执行规则修复；
3. 无法证明安全时，不传播原始正文，改为紧凑 `conflict_alert`；
4. 阻断结果写入 `failure_state`，只允许审查或有限重试；
5. 修复后的正常结果写入 `artifact_state`，并可继续进入记忆候选流程；
6. 发布 `downstream_fact_correction` 补偿事件，但不废弃仍然正确的当前
   MemoryView；
7. 原始错误正文只保留在冷审计中，采用归因仍按修复前正文计数。

`soft_deprecate` 只用于 Reviewer 证明当前 MemoryView 本身错误的情形。本阶段
发现的是 Agent 采用了该视图的历史值，因此若直接废弃当前正确视图，反而会破坏
事实版本链。

## 通用性边界

- 不识别 Question A、D1-D3 或任何业务题目；
- 不依赖 Planner、Writer、Reviewer 等固定角色名；
- 不对所有消息做全局字符串替换，只修改证据定位的冲突片段；
- 非结构化或不确定冲突不猜测正确改法，转入 `review_or_retry_only`。

## 新增指标

- `memory_adoption_guard_event_count`
- `memory_adoption_rule_repair_count`
- `memory_adoption_blocked_count`
- `memory_adoption_enforcement_failure_count`
- `memory_adoption_repaired_fact_count`

## 当前结论

该阶段补上了 TLC-Memory “发现错误采用”到“阻止污染传播”的工程闭环。
确定性门禁不能替代真实 Provider 和真实 AutoGen 的后续故障注入实验；它只证明
规则修复、阻断、状态写入和指标链路在受控输入下成立。

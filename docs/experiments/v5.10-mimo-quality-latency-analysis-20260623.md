- `agent_runtime/llm/agents.py`: LLM-side final-task instruction now uses the same rule.

| final_quality_retry_count | 0 | 1 | +1 |
| background_memory_wait_ms | 0 | 1,885.96 | +1.89s |

Per-suite latency:

| suite | latency delta | llm latency delta | prompt token change | completion token change |
| --- | ---: | ---: | ---: | ---: |
| A | +117.73s | +116.66s | -63.11% | +21.24% |
| B | +187.70s | +184.76s | -67.81% | +22.51% |

Interpretation:
- The latency increase is almost entirely inside LLM calls.
- Local runtime overhead is not the main bottleneck: background memory wait is only about 1.89 seconds across the whole run.
- Runtime_lite greatly reduces input/context cost, but it currently makes the same 100 agent LLM calls as the baseline, plus one final schema retry.
- Runtime_lite also asks agents to produce contract-compliant, more complete artifacts. That improves final quality, but it shifts part of the cost to completion generation.
- The current result is therefore not a communication-layer failure; it is a scheduling and request-shaping issue.

## 6. Latency Remediation Plan Without Shortening Final Output

Do not reintroduce output token caps for final deliverables. The previous truncation risk is real, and quality now depends on complete final answers.

Recommended changes:

1. Add per-agent latency instrumentation.
   - Record `agent_id`, `llm_latency_ms`, prompt tokens, completion tokens, retry count, and contract repair count in trace/CSV.
   - This is required before claiming a latency optimization as causal.

2. Re-check the MemoryManager LLM role, not the memory admission gate.
   - Memory admission is already rule-first in the v3.3+ path: `memory_card` and `claim_cards` enter MemoryCandidate / ClaimCandidate first, then deterministic admission decides whether they update MemoryView.
   - The remaining latency question is different: many tasks still include a `memory_manager` LLM role that generates a memory summary artifact.
   - v5.11 should measure whether this role is a true task participant or only an implementation convenience. If it is only producing data already available from Contract Guard fields, later versions can replace that LLM call with deterministic candidate extraction.
   - This reduces requests without cutting final answer length and keeps the planned "memory candidate pool -> admission gate -> memory pool" route intact.

3. Re-check reviewer call policy for non-final low-risk tasks.
   - Run deterministic schema coverage, conflict checks, and field completeness before asking the reviewer LLM.
   - For non-final tasks with valid schema and no conflict, persist a structured review record without a long reviewer generation.
   - Keep full LLM reviewer for A10/B10 and high-risk tasks.

4. Parallelize independent post-writer work.
   - After writer output is available, contract repair, schema coverage, artifact digest, memory candidate extraction, and reviewer preparation can run concurrently.
   - Reviewer should not wait for memory admission unless it needs the admitted memory in the same task.
   - This aligns with AutoGen's concurrent-agent / topic routing pattern and keeps the runtime layer framework-compatible.

5. Stabilize prompt prefixes for provider prompt caching.
   - Put stable system instructions, schema text, and contract template at the beginning.
   - Put task-specific prompt views and state refs after the stable prefix.
   - If a provider supports `prompt_cache_key`, expose it as an optional adapter field. If MiMo does not support it, keep the prompt order stable for future providers.

6. For local/openEuler deployment, evaluate vLLM-class serving optimizations.
   - PagedAttention / continuous batching helps when many LLM calls are served by a local model.
   - Speculative decoding can reduce generation latency without reducing final output length.
   - These are provider-side or local-serving optimizations, not required for the current MiMo API test.

## 7. Recommended Next Version

Do not jump to AutoGen adapter yet. The next engineering version should be:

```text
v5.11 latency instrumentation + MemoryManager/Reviewer call audit
```

Acceptance criteria:
- A10/B10 final answer length is not capped.
- A10/B10 quality judge score is not lower than v5.10.
- `llm_call_count` decreases from 101, or wall-clock latency decreases with repeated runs.
- `fallback_count=0`, `wrong_memory_hit_count=0`, `raw_access_count=0` remain unchanged.
- Provider token, end-to-end collaboration token, and judge score are reported together.

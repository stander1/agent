# v5.14l 类型化可靠性正式 Provider 回归

## 1. 阶段目标

v5.14k 已通过不调用 Provider 的机制验收，证明以下通用能力在确定性样例中
成立：

- 金额、时间和计数按量纲解析，禁止跨量纲比较；
- Reviewer 的阻断意见不能伪装成最终成果；
- 不确定或推断事实留在候选池，不能直接进入正式共享记忆；
- `retrieval_state` 和 `embedding_state` 必须来自框架真实输出字段；
- 匿名评分证据必须能在当前候选答案中定位。

v5.14l 不再增加生产机制，而是把这些能力放回真实 MiMo Provider、
A1-A10/B1-B10 完整连续任务和三组公平对照中，确认修复没有通过增加
Token、降低质量或修改实验问题来换取。

## 2. 冻结实验条件

以下条件与 v5.14j 完全一致：

| 项目 | 冻结值 |
|---|---|
| A/B 任务 | v5.14f 的 `question_A_formal.json`、`question_B_formal.json` |
| Agent 配置 | 原 A/B 配置文件 |
| Provider | MiMo 开发者计划 OpenAI 兼容端点 |
| 模型 | `mimo-v2.5` |
| 温度 | `0` |
| 最大轮次 | `9` |
| 分组 | Native、Observed、Managed |
| 质量口径 | 综合盲评与技术盲评取较低分 |
| 旧门槛 | v5.14j 的成本、质量、交付、记忆和协议门槛全部原样保留 |

Native 表示原生 AutoGen；Observed 表示 AgentLite 只观察不改写；
Managed 表示 AgentLite 接管协作。评分调用不计入运行时成本。

## 3. 新增验收门禁

### 3.1 类型化数量

A6 曾把“首日 10 点后出发”等时间数字错误地当成预算数字。v5.14l
检查所有成功交付的守卫原因，任何再次出现
`budget_upper_bound=30` 的跨量纲结果都会导致验收失败。

### 3.2 审查闭环

A7、A10 曾把 Reviewer 的修订清单当作最终答案。v5.14l 对每个
`delivery_valid=true` 的最终内容重新运行通用交付守卫。若内容仍要求
Writer 修订、明确声明尚未完成，验收失败。

### 3.3 认识状态准入

B8 明确包含“预期结果”和“待执行查询”。系统必须：

1. 将未观察、未确认事实记录为候选；
2. 将其 `admission_status` 保持为 `pending_confirmation`；
3. 不将其写入正式共享记忆；
4. 在报告中记录 `memory_epistemic_deferred_count`。

该门禁不要求所有任务都产生不确定事实，只要求冻结任务中本来存在的
不确定事实确实经过候选池。

### 3.4 真实结构化状态

B2 和 B7 本身要求输出真实检索与向量元数据，因此不需要修改任务：

- B2 应生成 `retrieval_state`；
- B7 应生成 `embedding_state`；
- 向量状态必须包含查询向量 ID、维度、候选引用和分数；
- 状态载荷的 `raw_content_sha256` 必须与冷层审计原文重新计算一致；
- 缺少真实引用时不能只凭语义动作伪造状态。

### 3.5 回归焦点

逐任务盲评焦点为 A2、A4、A6、A7、A10、B8、B9、B10。每项均必须：

- 运行时交付有效；
- 盲评认为交付完整；
- Managed 分数不低于 7；
- Managed 相对 Native 的差值不超过冻结容忍范围；
- 无 critical/high 阻断发现；
- 最终内容不含 AgentLite 内部协议标记。

## 4. 成本和公平性

旧门槛不因 v5.14k 修复而放宽：

- Managed Provider Token 相对 Native 至少降低 15%；
- Managed 端到端协作 Token 至少降低 15%；
- Managed 总体质量相对 Native 的劣化不超过 0.3；
- Managed 完整交付数不得少于 Native；
- 不限制正常输出长度，不减少轮次，不增加隐藏 LLM 修复调用。

端到端协作成本仍按以下项目合计：

```text
direct_message_tokens
+ prompt_view_tokens
+ retrieved_memory_tokens
+ control_llm_tokens
+ retry_tokens
```

## 5. 证据与边界

验收器同时绑定：

- v5.14j 预注册文件哈希；
- v5.14k 机制验收器哈希；
- v5.14k 机制发布提交；
- 正式任务和 Agent 配置哈希；
- 本次运行提交必须是 v5.14k 发布提交的后代。

该阶段仍是一次正式运行，只能证明本次冻结条件下是否通过，不能替代多次
独立重复实验的方差和置信区间分析。

## 6. 技术评分证据恢复

技术评分模型有时会正确识别问题，但把 evidence 改写为近义表述。直接接受
近义表述会破坏“证据必须属于当前答案”的边界；单纯重复提示又可能连续失败。
评分器因此采用以下恢复协议：

1. 第一次审查仍要求 evidence 逐字来自当前答案；
2. 若仅证据归属失败，将每个候选的当前答案切分为 `E001` 等局部锚点；
3. 评分模型必须返回同一候选的 `evidence_id`；
4. 程序从锚点回填当前答案原文，并再次执行精确包含校验；
5. 未知锚点、跨候选锚点及历史答案文本仍会被拒绝；
6. 分数范围、严重级别、交付判定与匿名映射均不改变。

`resume_technical_audit.sh` 会复用已经校验的逐任务 checkpoint，仅续跑未完成
的技术评分，并在 `system/scoring-recovery-history.txt` 中记录恢复提交和时间。

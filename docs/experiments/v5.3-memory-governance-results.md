# v5.3 Memory Compaction 与 Conflict Resolver 记录

日期：2026-06-22

## 1. 本轮目标

根据 `docs/competition/工程校验-二次复核-外部审计问题核对.md`，本轮补齐 TLC-Memory 的核心治理缺口：

1. Semantic Schema Registry 不能只停留在常量和 alias dict。
2. Canonical Claim Form 需要有可落地的 Lite 结构。
3. MemoryView 不能只是简单拼接最近几条 summary。
4. 同 slot / 同 subject 的冲突 Claim 需要有确定性处理。
5. Batch Compaction 需要成为显式方法，而不是隐含在 `_upsert_memory_view()` 中。

## 2. 新增 SchemaRegistryLite

新增模块：

```text
agent_runtime/memory/schema_registry.py
```

新增对象：

- `SchemaRegistryLite`
- `SlotPolicy`
- `CanonicalClaimLite`
- `RegistrySlotResolution`

当前能力：

1. 标准 slot 解析。
2. alias mapping 解析。
3. slot policy 查询。
4. Canonical Claim Lite 生成。

`ClaimCard` 新增 CCF-lite 字段：

```text
claim_type
value
polarity
modality
temporal_scope
schema_version
conflict_policy
```

## 3. ConflictResolverLite

`MemoryStoreLite._upsert_memory_view()` 现在会调用 `_resolve_claim_conflict()`。

当前规则：

```text
同 slot + 同 subject:
  选择 confidence 更高的 Claim 作为 active；
  confidence 相同则选择 created_at 更新的 Claim；
  被替代的 Claim 标记为 superseded；
  对应 MemoryObject 同步标记为 superseded 并提升 version_id。
```

这让 MemoryView 不再把冲突 Claim 都当作 active 使用。

## 4. BatchCompactionEngine-lite

新增：

```text
MemoryStoreLite.run_compaction(slot_id=None)
```

返回：

```text
MemoryCompactionReport
```

当前 compaction 会：

1. 扫描目标 MemoryView。
2. 仅保留 status 为 `active` 的 Claim。
3. 根据 active claims 重建 `prompt_summary`。
4. 统计 `new_claim_count`、`merged_claim_count`、`superseded_claim_count`。
5. 写入 `_compaction_log`。

## 5. MemoryView 增强

`MemoryView` 新增：

```text
historical_claim_ids
conflicting_claim_ids
resolution_status
downstream_policy
```

当前下游策略为：

```text
use_active_claims_only
```

也就是 Prompt View 默认只使用 active claims，superseded claims 仍留在 audit 层用于追溯。

## 7. 已解决与未解决

已解决：

1. `SchemaRegistryLite` 落地。
2. `CanonicalClaimLite` 落地。
3. `ConflictResolverLite` 落地。
4. `BatchCompactionEngine-lite` 落地。
5. MemoryView 增加 active / historical / conflict 分层字段。

仍未解决：

1. Semantic Schema Registry 仍是静态 Lite，不支持动态注册和 embedding similarity matching。
2. Conflict Resolver 当前只有 highest_confidence_then_latest 策略。
3. Batch Compaction 当前是规则版，不调用 LLM，也没有复杂事实融合。
4. State Lifecycle / GC / Readiness Barrier 仍需 v5.4 继续处理。

## 8. 下一步建议

下一步进入：

```text
v5.4 State Lifecycle / GC / Readiness Barrier
```

优先实现：

1. 状态生命周期状态机。

5. `ReadinessBarrier-lite`。

这一步补齐 SHP-State 的长任务稳定性和 CMJCC 的信息就绪门控。

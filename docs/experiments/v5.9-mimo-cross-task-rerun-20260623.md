# v5.9 MiMo 跨任务 A/B 重新实验报告

日期：2026-06-23

## 1. 实验目的

本轮重新运行 A、B 两组连续任务，目标是验证 v5.9 工程修复后，`baseline_text` 与 `runtime_lite` 在真实 MiMo Provider 下的端到端差异是否仍然成立。

本轮重点不只看“直接消息 token”，而是看端到端协作成本：

```text
end_to_end_collaboration_tokens =
  direct_text_tokens
+ prompt_view_tokens
+ retrieved_memory_tokens
+ control_llm_tokens
+ retry_tokens
```

这样可以避免把 Agent 间文本消息减少，但把成本转移到 Memory/State 读取里的假优化。

## 2. 实验口径

- Provider：MiMo Token Plan，`mimo-v2.5`
- API 地址：`https://token-plan-cn.xiaomimimo.com/v1`
- Tokenizer：`tiktoken:cl100k_base`，版本 `0.13.0`
- 任务：A1-A10 旅行规划连续任务 + B1-B10 安全审计连续任务
- 模式：`baseline_text` 与 `runtime_lite`
- 运行方式：A、B 在同一个 runtime 中连续执行
- 输出目录：`runs/v5.9-mimo-cross-task-20260623-102055`

运行命令：

```powershell
F:\software\anaconda\envs\multi-agent-demo\python.exe -u examples\run_cross_task_eval.py --suite A --suite B --rounds 1 --mode both --config configs\llm.mimo.example.json --max-retries 4 --retry-backoff-seconds 3 --output-dir runs\v5.9-mimo-cross-task-20260623-102055
```

说明：本轮在当前工作区运行。工作区中含有监控快照相关未提交改动，会在任务过程中写入 `pool_snapshot_latest.json`。这些改动只增加观测文件输出，不改变 Agent prompt、协议校验、状态/记忆治理逻辑；延迟数据因此代表“当前带监控快照工作区”的实际运行结果。

## 3. A+B 总结果

| 指标 | baseline_text | runtime_lite | 变化 |
|---|---:|---:|---:|
| task_runs | 20 | 20 | 0 |
| success_count | 20 | 20 | 0 |
| latency_ms | 3,012,518 | 1,801,653 | -40.19% |
| llm_total_tokens | 11,677,277 | 249,922 | -97.86% |
| end_to_end_collaboration_tokens | 17,103,196 | 164,398 | -99.04% |
| direct_text_tokens | 352,426 | 61,862 | -82.45% |
| prompt_view_tokens | 16,750,770 | 87,604 | -99.48% |
| retrieved_memory_tokens | 0 | 14,932 | 新增 |
| memory_hit_count | 0 | 44 | 新增 |
| useful_memory_hit_count | 0 | 44 | 新增 |
| wrong_memory_hit_count | 0 | 0 | 0 |
| fallback_count | 0 | 0 | 0 |
| raw_access_count | 0 | 0 | 0 |

结论：

1. `runtime_lite` 在成功率不下降的前提下，将 Provider 统计的 LLM token 从 `11,677,277` 降到 `249,922`，下降 `97.86%`。
2. 端到端协作 token 从 `17,103,196` 降到 `164,398`，下降 `99.04%`。
3. `runtime_lite` 新增了 `14,932` 个记忆读取 token，但远小于 baseline 的完整历史 prompt 成本，没有出现明显 cost shifting。
4. `fallback_count=0`，说明本轮没有进入降级兜底路径。
5. `raw_access_count=0`，说明 runtime_lite 没有依赖冷层原始大正文读取来维持效果。

其中：

- `fallback_count`：降级兜底次数。当模型输出无法按协议修复时，系统用 degraded message 保住流程不中断。这里为 0，说明协议稳定。
- `raw_access_count`：原始大正文读取次数。这里为 0，说明系统主要通过摘要、证据片段、Prompt View 和 Memory View 工作。
- `useful_memory_hit_count`：有效记忆命中次数。这里等于 `memory_hit_count`，说明命中的记忆都进入了有效使用路径。

## 5. 协议与治理指标

| 指标 | baseline_text | runtime_lite |
|---|---:|---:|
| provider_response_retry_count | 1 | 2 |
| provider_response_degraded_count | 0 | 0 |
| contract_guard_checked_count | 0 | 100 |
| contract_schema_valid_count | 0 | 100 |
| deliverable_schema_required_count | 0 | 28 |
| deliverable_schema_hit_count | 0 | 28 |
| deliverable_schema_complete_count | 0 | 2 |
| background_memory_job_count | 0 | 60 |
| background_memory_completed_count | 0 | 60 |
| preflight_validation_count | 0 | 20 |
| read_lease_acquire_count | 0 | 260 |

解释：

- `provider_response_retry_count`：Provider Response Guard 触发的响应重试次数。本轮 baseline 为 1，runtime_lite 为 2，但最终都没有 degraded。
- `contract_guard_checked_count`：Contract Guard 检查次数。runtime_lite 每次 Agent handoff 都经过协议检查，共 100 次。
- `contract_schema_valid_count`：协议 schema 合法次数。本轮 runtime_lite 为 100/100。
- `deliverable_schema_complete_count`：最终交付 schema 完整任务数。本轮 A10、B10 两个最终任务均完整。
- `preflight_validation_count`：高成本写作前的前向校验次数。本轮 runtime_lite 共 20 次，没有 block。
- `read_lease_acquire_count`：状态读取租约获取次数。本轮 runtime_lite 共 260 次，说明读租约路径已实际参与运行。

## 7. 最终正文与质量裁判

本轮 `deliverables.json/jsonl` 已保存 40 条最终输出，A10/B10 的 baseline 与 runtime_lite 都有完整正文：

| 任务 | 模式 | 最终 agent | content_chars |
|---|---|---|---:|
| A10 | baseline_text | reviewer | 2,248 |
| A10 | runtime_lite | reviewer | 2,566 |
| B10 | baseline_text | reviewer | 2,083 |
| B10 | runtime_lite | reviewer | 3,115 |

独立 MiMo 质量裁判文件：

```text
runs/v5.9-mimo-cross-task-20260623-102055/quality_judge_mimo_a10_b10.json
```

裁判输出显示 A10、B10 均判定 `baseline_text` 更优，但裁判理由暴露了一个更关键的问题：两种模式的“最终交付类型”不完全同口径。

抽查正文发现：

- A10 `baseline_text` 最终输出是 ReviewerAgent 审查报告，开头为“ReviewerAgent 审查报告：任务A10”。
- A10 `runtime_lite` 最终输出是“最终修订版旅行手册与决策日志”正文。
- B10 `baseline_text` 最终输出是 ReviewerAgent 审查报告。
- B10 `runtime_lite` 最终输出是“最终合成安全审计手册”正文。

因此，本轮质量裁判不能直接解读为“baseline 语义质量更高”。更准确的结论是：

> 成本、协议、成功率指标已经稳定；但最终交付物选择口径仍需校准。下一步应把 Writer 正文、Reviewer 审查报告和最终对外交付物分开持久化，再用同一种交付类型做 LLM judge。

## 8. 当前结论

v5.9 工程修复后的真实 MiMo 跨任务 A/B 重新实验显示：

1. `runtime_lite` 在连续 A->B 场景下仍显著降低 LLM token、端到端协作 token 和延迟。
2. 记忆读取成本没有吞掉节省收益，未出现明显 cost shifting。
3. Contract Guard、Provider Response Guard、Read Lease、Preflight、异步记忆写入等机制都进入了真实运行路径。
4. `fallback_count=0`、`wrong_memory_hit_count=0`、`raw_access_count=0`，说明本轮协议稳定、记忆命中未污染输出、未靠冷层原始正文撑结果。
5. 剩余主要问题不是低开销机制，而是最终交付口径：需要明确“最终给用户/评委看的交付物”到底取 Writer 正文、Reviewer 修订后正文，还是 Reviewer 审查报告。

## 9. 下一步建议

进入 v5.10 小修，不急着接 AutoGen：

1. 增加 `deliverable_role`：区分 `draft_answer`、`review_report`、`final_answer`。
2. 修改最终任务输出策略：A10/B10 必须持久化同口径 `final_answer`。
3. 保留 Reviewer 审查报告，但不要把它和对外最终手册混成同一个质量裁判对象。
4. 重新只跑 A10/B10 或小范围 A8-A10、B8-B10，验证最终交付口径修正。
5. 再做一次独立质量裁判，把质量结论写进比赛报告。

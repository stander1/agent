# v5.13m 普通开发者有状态 A1-A10 公平实验报告

## 1. 结论摘要

本轮在同一台 Windows 主机、同一 MiMo 模型、同一 AutoGen 应用、同一 Agent 配置和同一 A1-A10 连续问题链上依次运行三组：

- `native`：原生 AutoGen；
- `observed`：AgentLite 只观察，不改写消息；
- `managed`：AgentLite 接管真实消息传输、状态和共享记忆。

实验得到两个同时成立、但不能混为一谈的结果：

1. **真实协作载荷降低 20.03%**：接管组在真实改写审计范围内，从原生传输等价成本 193,672 Token 降至端到端协作成本 154,876 Token。
2. **供应商实际总 Token 增加 24.01%**：原生组为 517,444，接管组为 641,657。当前版本已经压缩底层协作载荷，但尚未把该收益稳定转化为 LLM 账单下降。

三次不同匿名排列的有状态盲评均值为：原生组 9.2、观察组 10.0、接管组 9.7。接管组本轮没有观察到质量下降，但观察组在不改写消息的情况下得分最高，说明单次生成和 LLM 裁判仍有明显波动，不能把本轮写成“质量显著提升”。

## 2. 代码与实验条件

- 实验代码版本：`8576cb4 Harden chronology grounding and final delivery`；
- 模型：`mimo-v2.5`；
- 温度：`0`；
- 每题最大团队轮次：`9`；
- 连续任务：`question_A_sequence.json`，A1-A10 共 10 题；
- Agent：同一组 Planner、Writer、Reviewer；
- 三组均复用一个 AutoGen Team 实例；
- Provider Token 直接读取模型接口 `usage`，不是字符估算；
- 三组顺序执行，避免并发请求互相争抢网络资源。

运行目录：

```text
runs/ordinary-developer/v5.13m-fair-20260720-202234/
.agentlite-exp/v5.13m-fair-20260720-202234/
```

## 3. Provider 实际 Token 与延迟

| 指标 | 原生组 | 观察组 | 接管组 |
|---|---:|---:|---:|
| 有效交付 | 10/10 | 10/10 | 10/10 |
| LLM 调用 | 30 | 30 | 33 |
| 输入 Token | 443,462 | 474,218 | 550,147 |
| 输出 Token | 73,982 | 75,009 | 91,510 |
| 总 Token | 517,444 | 549,227 | 641,657 |
| 相对原生变化 | - | +6.14% | **+24.01%** |
| Provider 重试 | 0 | 2 | 6 |
| 总耗时 | 1,039.4 s | 1,118.5 s | 1,658.6 s |
| 相对原生耗时 | - | +7.61% | **+59.58%** |

不能把观察组相对原生的 +6.14% 解释为 AgentLite 观察开销。观察模式没有修改模型输入，差异来自三组独立生成后，输出长度和后续历史自然分叉，以及两次 Provider 重试。

### A10 异常放大

接管组 A1-A9 与原生组对比：

- 原生组：407,782 Token，27 次调用，909.6 s；
- 接管组：420,331 Token，27 次调用，1,010.9 s；
- 接管组 Token 增加 3.08%，耗时增加 11.13%。

A10 单题中，接管组首轮 Reviewer 正确发现预算合计 2,640 元超过 2,600 元硬约束，因此 AutoGen 团队进入第二个 Planner-Writer-Reviewer 周期：

| A10 指标 | 原生组 | 接管组 |
|---|---:|---:|
| LLM 调用 | 3 | 6 |
| 总 Token | 109,662 | 221,326 |
| Provider 重试 | 0 | 5 |
| 耗时 | 129.7 s | 647.7 s |
| 最终盲评 | 10 | 10 |

多出的三次协作调用是 AutoGen 团队依据相同终止条件进行的质量修订，不是 AgentLite 的交付守卫追加调用；其中 A10 Writer 的一次调用经历 4 次网络重试。它既保住了最终质量，也显著放大了本轮 Token 和延迟。

## 4. AgentLite 真实通信口径

接管组报告中的真实改写事件为 43 次，成本拆分如下：

| 成本项 | Token | 含义 |
|---|---:|---|
| 原生传输等价成本 | 193,672 | 同一批真实改写事件若保留原生内容的传输成本 |
| 短控制消息 | 31,523 | Agent 间实际传递的压缩消息 |
| Prompt View | 108,017 | 下游角色读取的裁剪状态视图 |
| 记忆读取 | 15,336 | 实际注入 Prompt View 的共享记忆 |
| AgentLite 端到端协作成本 | 154,876 | 上述三项之和 |
| 节省 | **38,796** | 相对原生传输等价成本 |
| 节省率 | **20.03%** | 已发生的真实改写，不是 shadow 理论值 |

该口径证明“底层传输与状态读取合计更小”，但它不等于 Provider 的完整输入 Token。模型还会收到系统提示、角色提示、AutoGen 自身历史和当前生成上下文，因此本轮出现了“通信载荷下降、Provider 总账单上升”。这正是必须同时公布两种口径的原因。

## 5. 共享记忆结果

| 指标 | 结果 |
|---|---:|
| 记忆查询 | 43 |
| 命中 | 39 |
| 命中率 | 90.70% |
| 实际注入 | 25 |
| 命中后注入率 | 64.10% |
| 已证明有效命中 | 0 |
| 错误命中 | 0 |
| 尚未评估命中 | 25 |

这表明共享记忆检索和成本门禁已经实际工作，但当前追踪还没有下游引用证据，25 次注入全部属于 `unassessed`。因此不能仅凭 90.70% 命中率宣称记忆有效；下一版应补“哪条记忆被哪个输出采用”的证据链。

## 6. 有状态质量盲评

最初匿名包只包含历次用户问题和当前答案，无法证明同一系统的目的地是否跨轮连续。本轮发现后修正为：

- 每组使用跨任务稳定、无组名的匿名 `track_id`；
- 裁判同时读取该轨道上一轮与当前交付物；
- 分数先写入冻结文件，再读取组别映射解盲；
- 使用匿名顺序 513、514、515 重复三次，控制候选位置偏差；
- 裁判 Token 单独统计，不计入运行时成本。

评分维度为任务完成度 0-4、上下文保持 0-3、正确性与一致性 0-2、清晰度与可执行性 0-1。

| 组别 | 三次均分 | 均值 | 三次完整交付数 |
|---|---|---:|---|
| 原生组 | 9.5 / 9.2 / 8.9 | 9.2 | 9 / 9 / 9 |
| 观察组 | 10.0 / 10.0 / 10.0 | 10.0 | 10 / 10 / 10 |
| 接管组 | 9.6 / 9.8 / 9.7 | **9.7** | 10 / 10 / 10 |

三次裁判共使用 408,171 Token，仅为离线评测成本。接管组相对原生组均值高 0.5 分，但由于只有一轮三组生成、裁判也是同一 MiMo 模型，正式结论只能是：**本轮没有观察到 AgentLite 导致的质量下降，且连续上下文交付保持完整；尚不足以证明稳定质量提升。**

主要波动集中在 A1-A3。A4-A10 三组在三个匿名顺序中基本均为满分。接管组 A3 的预算表达存在轻微内部不一致，说明记忆连续并不能自动保证算术和预算口径完全正确。

## 7. 本地运行时开销

用总耗时减去 Provider LLM 耗时：

- 原生组本地开销约 0.122 s；
- 观察组约 2.410 s；
- 接管组约 5.715 s，占接管组总耗时约 0.34%。

状态池、记忆检索和改写本身不是本轮主要延迟来源。主要延迟来自模型生成、A10 额外修订周期和 Provider 重试。

## 8. 协议与可复现材料

- 三组均为 10/10 严格最终交付；
- 没有 `degraded_fallback`；
- 没有由领域规则触发的语义重试；
- A10 的额外周期来自 Reviewer 正常审查；
- 每一步 Planner、Writer、Reviewer 的可见输出都保存在 `sequence_result.json` 和 `tasks/A*/run_result.json`；
- `llm_usage.jsonl` 保存每次调用的 Token、耗时、重试和 Agent 元数据，不保存隐藏推理；
- AgentLite 报告保存在观察组和接管组的 `agentlite-report.json/.md/.csv`。

## 9. 最终判断与下一步

v5.13m 已经证明 AgentLite 能在真实 AutoGen 连续任务中接管消息、状态和共享记忆，并把真实协作载荷降低 20.03%，同时保持 10/10 可交付和本轮质量不下降。

它还没有证明“接管后 Provider 总 Token 一定降低”。下一步不应继续扩展框架，而应解决两个具体问题：

1. 对比 AgentLite Prompt View 与 AutoGen 原生历史，消除同一事实同时存在于框架历史、状态视图和记忆注入中的重复；
2. 增加记忆采用证据，使 `useful_memory_hit_count` 可被真实输出引用更新，并据此淘汰无用注入。

完成后应对 A/B 两条连续任务各运行至少 3 个独立重复，再报告均值、标准差和质量置信边界。

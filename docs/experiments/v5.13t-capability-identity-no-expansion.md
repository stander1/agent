# v5.13t 能力身份归并与上下文不膨胀

## 1. 修改依据

v5.13s openEuler 实验虽然 18/18 项验收通过，但进一步审计发现：

- 16 次业务 LLM 调用产生了 410 条 `capability_profile_updated` 事件；
- 4 个业务 Agent 被 AutoGen UUID 运行实例扩展为 11 个画像 ID；
- MemoryView 从 6762 Token 变为 7111 Token，增加 5.16%；
- 当前任务视图从 1472 Token 变为 1969 Token，增加 33.76%。

这不表示共享记忆或能力画像方向错误，而是画像身份、事件语义和视图选择器仍不够严格。

## 2. 本轮修改

### 2.1 能力画像事件去重

`capability_profile_updated` 现在只在以下情况写入：

1. 逻辑 Agent 首次被运行时观测到；
2. 角色描述、声明能力、工具或输入输出契约真正变化；
3. 工具同步等变化使 `profile_version` 递增。

普通钩子重复经过同一对象、执行反馈刚刚提高版本号后再次注册，均不再重复写画像更新事件。执行成功率、Schema 可靠性、成本和时延仍由 `capability_profile_feedback` 独立记录。

### 2.2 AutoGen 逻辑 Agent 与运行实例分离

对于 `AgentName_<uuid>_<same-uuid>` 形式的 `ChatAgentContainer`：

- 画像主键归并为 `AgentName`；
- UUID 名称保存在 `instance_aliases`；
- UUID 容器只登记运行实例，不覆盖业务 Agent 的角色、工具和能力；
- Team、GroupChat Manager 和 Runtime 标记为 `registry_scope=system`；
- 业务 Agent 标记为 `registry_scope=business`；
- 默认能力路由只从业务画像中选择候选者。

该规则不依赖 Planner、Writer、Reviewer 等固定角色名，任意开发者自定义 Agent 名称均使用同一套逻辑身份规则。

### 2.3 最小角色视图不膨胀

能力视图生成后不再直接注入，而是执行 Token 级选择：

```text
candidate_tokens < source_tokens
    -> 注入 capability_minimized 候选视图
否则
    -> 注入 source_no_expansion 语义等价来源视图
```

来源视图是候选视图的语义超集，因此回退不会丢失必要上下文。能力、动作、字段覆盖等元数据继续留在控制面和 Trace 中，不为了说明角色而重复进入 Prompt。

新增指标包括：

- `memory_role_view_candidate_tokens`；
- `memory_no_expansion_fallback_count`；
- `current_task_role_view_candidate_tokens`；
- `current_task_no_expansion_fallback_count`；
- `registered_system_profile_count`；
- `registered_total_profile_count`。

## 3. 自动验收增强

v5.13s 验收器新增四项硬检查：

1. 业务画像只能是配置中的四个逻辑 Agent；
2. 画像更新事件数量不得再次随钩子调用次数爆量；
3. 实际记忆角色视图 Token 不得大于来源 MemoryView；
4. 实际当前任务角色视图 Token 不得大于原任务文本。

## 4. 本机验证

- 62 项相关回归测试通过；
- `compileall` 通过；
- `git diff --check` 通过；
- 全量 201 项测试中，其余错误来自当前 Windows Python 缺少 `autogen-agentchat`、`pydantic`、`tiktoken`，不是本轮断言失败；完整依赖验收继续在 openEuler 虚拟机执行。

## 5. 未在本轮掩盖的问题

v5.13s 中 60 次底层契约回退仍需按消息类型分类。本轮没有通过关闭 Schema、类型保持或消息结构守卫来提高改写次数；后续只扩展能够证明类型安全的 AutoGen 消息编解码器。

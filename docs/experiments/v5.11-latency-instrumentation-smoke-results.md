# v5.11 Latency Instrumentation Smoke Results

Date: 2026-06-23

## Purpose

v5.10 showed that the latency increase is mostly inside LLM calls, but the evidence was still task-level. v5.11 adds per-agent latency instrumentation so later MiMo A/B runs can show whether the bottleneck is in Planner, Retriever, Writer, Reviewer, MemoryManager, or local runtime overhead.

This version does not change scheduling, does not add parallel execution, and does not shorten final answers.

## Added Metrics

Each row in `agent_metrics.csv` / `agent_metrics.json` records:

```json
{
  "agent": "writer",
  "task_id": "A10",
  "llm_prompt_tokens": 0,
  "llm_completion_tokens": 0,
  "llm_total_tokens": 0,
  "llm_wall_time_ms": 0,
  "ttft_ms": 0,
  "tokens_per_second": 0,
  "local_state_read_ms": 0,
  "local_memory_search_ms": 0,
  "artifact_digest_ms": 0,
  "schema_check_ms": 0,
  "retry_count": 0,
  "raw_access_count": 0
}
```

Notes:
- `ttft_ms` is currently `0` because the provider client uses non-streaming requests (`stream=false`). A real TTFT value requires streaming or provider-side timing.
- `tokens_per_second` is completion-token throughput: `llm_completion_tokens / llm_wall_time_seconds`.
- Local runtime overhead is also represented by an `agent=local_runtime` row so reports can draw a separate "Local runtime overhead" bar.

## MemoryManager Clarification

`memory_manager` is an experimental agent role. It is not the same thing as the memory admission mechanism.

Current architecture:

```text
Agent output / Contract Guard memory_card
-> MemoryCandidate / ClaimCandidate
-> deterministic admission rules
-> admitted MemoryView / MemoryRef
```

Therefore, memory admission is already rule-first. The remaining v5.11 question is whether the `memory_manager` LLM role is still necessary on every task. If the Contract Guard control header already contains a high-quality `memory_card` and `claim_cards`, later versions can remove or gate this LLM role without changing the planned admission layer.

## Reviewer Clarification

`reviewer` is a planned agent role and appears from the early v0 planning as the audit / review stage. Later versions also introduced Reviewer Guard behavior for final deliverable schema repair.

Current distinction:

| term | meaning |
| --- | --- |
| ReviewerAgent | LLM or deterministic role that reviews prior outputs |
| Reviewer Guard | rule/check layer that detects missing final fields and can trigger a short-context repair |
| final_answer | writer-authored final deliverable used for quality judging |
| review_report | reviewer-authored audit report preserved as evidence |

The latency question is not whether reviewer exists in the design. It is whether every non-final low-risk task must call a full LLM reviewer, or whether deterministic checks can cover some cases while keeping full reviewer calls for A10/B10 and high-risk tasks.

## Report Chart Target

The next MiMo run should aggregate `agent_metrics.json` into:

```text
Planner latency
Retriever latency
Writer latency
Reviewer latency
MemoryManager latency
Local runtime overhead
```

Expected evidence shape:
- `local_runtime.local_memory_search_ms + local_state_read_ms + artifact_digest_ms + schema_check_ms` should be small.
- `raw_access_count` should remain 0.
- LLM wall time should concentrate in Writer / Reviewer / MemoryManager if completion generation is the real bottleneck.
- If MemoryManager is large, the next optimization should be a call-policy change, not a memory-admission rewrite.

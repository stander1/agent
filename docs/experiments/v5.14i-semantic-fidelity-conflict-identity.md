# v5.14i 语义保真、冲突身份与协议隔离

## 1. 根因来源

v5.14h 的冻结口径正式回归证明成本下降仍然成立，但质量与交付门禁失败。
逐条复核 Provider 输出、Agent 输入、MemoryView、冲突守卫和最终交付后，
确认存在三个通用缺陷：

1. `constraint.budget` 同时承载预算上限、预算总计和预算分项，不同事实被当成
   同一 Claim 修订链；
2. active 与 historical 中语义和值完全相同的事实仍进入冲突分类，导致正常
   完整输出被替换为内部冲突包；
3. 当前任务保真只校验输入视图，最终交付守卫主要校验结构、引用和预算边界，
   因而可能接受回答旧阶段任务的完整文本。

## 2. 通用修复

### 2.1 预算 CCF 分面

规范槽位继续使用 `slot.project.requirement`，但通过 scope 区分：

- `constraint.budget_upper_bound`：用户预算上限或红线；
- `estimate.budget_total`：当前方案估算总额；
- `allocation.budget.<component>`：住宿、活动、礼物等分项金额。

Markdown 预算表按表头和行标签确定性抽取，不调用 LLM。动态中文 scope 在
Schema Registry 和 Claim Identity 中保留，不再因 ASCII 归一化而互相折叠。

### 2.2 冲突证据去重与完整修复

结构化冲突归因先排除 slot、scope、normalized value 和 polarity 全部相同的
active/historical 事实。规则修复要求每个已匹配历史跨度均被成功替换；只修复
一个跨度而遗漏另一个时，状态保持 `blocked`。

详细冲突原因、active facts 和补偿事件只写 trace/failure_state。模型侧不再
接收 `AGENTLITE_MEMORY_CONFLICT` JSON，也不会回放被拒绝的原正文；仅返回
不含协议字段的短安全暂缓说明，并由最终交付守卫明确拒绝其成为最终答案。

### 2.3 当前任务输出保真

最终交付守卫将“当前 request”和“历史 grounding contexts”分开：

- 当前 request 用于提取强交付锚点；
- 历史上下文只用于引用真实性和数值边界验证；
- 强制输出的 snake_case artifact/field 必须出现在最终正文；
- 明确要求比较全部候选且提供编号列表时，候选锚点必须进入最终正文；
- 没有强锚点的开放式普通任务保持原有行为，避免领域写死。

AutoGen 终止器始终以最新用户任务作为当前 request，旧任务只作为历史证据。

### 2.4 协议卫生观测

`model_visible_protocol_marker_count` 从只统计输入重写扩展为三个表面：

- `model_visible_input_protocol_marker_count`；
- `model_visible_agent_output_protocol_marker_count`；
- `model_visible_final_output_protocol_marker_count`。

会话报告保留总数和三个分项，避免内部包已经出现在输出中但报告仍显示 0。

## 3. 非目标

- 不增加 A/B、旅游、审计实体或固定 Planner/Writer/Reviewer 名称判断；
- 不通过提高轮次掩盖冲突分类错误；
- 不修改冻结正式任务、Agent 提示词、模型参数或评分标准；
- 本阶段不调用 Provider，不宣称真实质量已经恢复。

## 4. 下一阶段门槛

只有 v5.14i openEuler 机制验收全部通过，才进入相同冻结口径的 Provider 正式
回归。正式回归重点观察：

1. A2/A4 不再接受旧阶段答案；
2. A10 不再把预算上限、估算总额和分项金额互相替换；
3. B10 不再因相同 active/historical 值触发冲突循环；
4. 三个协议卫生分项均为 0；
5. 成本下降仍通过且 Managed 质量恢复到非劣门槛。

# v3.1 Final Deliverable Schema 实验记录

## 版本定位

v3.1 不是新增一套创新方案，而是把原方案中的以下能力落到最终交付质量控制层：

- Schema Registry：为不同任务域注册最终交付 schema。
- Agent Output Contract：最终收束任务必须覆盖 schema-required sections / fields。
- MemoryView / Deliverable View：最终任务读取裁剪后的可交付视图，而不是展开完整历史 raw content。
- Reviewer Guard：Reviewer 在发现 schema 缺项时可触发一次 Context-Pruned Final Schema Retry。

本轮主要解决 v3 暴露的问题：通用 Deliverable View 能改善证据链类任务，但对 A 组旅行手册这种强格式、强约束最终交付仍不够。

## 关键实现

新增 `agent_runtime/core/deliverable_schema.py`：

- `schema.travel.final_handbook.v1`
- `schema.security.final_audit.v1`
- `schema_for_task(task)`
- `render_schema_prompt(schema)`
- `schema_coverage(schema, text)`
- `schema_field_coverage(schema, text)`

运行时变化：

- 只有 `A10` / `B10` 这类最终收束任务触发 Final Deliverable Schema。
- Writer / Reviewer / MemoryManager 的最终任务 prompt 会注入 Final Deliverable Schema。
- Schema 覆盖统计支持英文字段名和中文别名。
- Reviewer 若缺字段，会触发一次短上下文修复，只传缺失字段、Schema、Deliverable View 和 Reviewer 初稿片段。
- 最终收束任务的输出长度单独放宽，避免“短摘要限制”和“完整交付 schema”冲突。

模型：`mimo-v2.5`

```text
https://token-plan-cn.xiaomimimo.com/v1
```

正式输出目录：

```text

runs/v3.1-security-b1-b10-mimo25-rerun2
```

命令参数核心差异：

```text
--rounds 1
--mode both
--max-completion-tokens 900
--max-retries 5
--retry-backoff-seconds 3
```

说明：v3.1 为了验证最终交付 schema 的完整性，将 `max_completion_tokens` 从早期实验的 360 提高到 900。因此 v3.1 与 v3/v2.3 的成本对比不是严格同输出预算消融；它更接近比赛展示中的“完整交付模式”。

## 当前结论

v3.1 证明：

```text
Final Deliverable Schema 可以在低通信开销下显著提高最终交付结构完整性。
```

但也暴露：

```text
结构完整性不等于领域细节充分。
```

对 A 组这类旅行/规划任务，后续需要继续增强：

- MemoryView 中保留更高价值的具体执行事实，而不仅是摘要。
- 对预算、交通、住宿、餐饮等字段建立更细粒度的领域 Slot。
- 在最终交付前加入“细节充分性”而不仅是“字段覆盖率”的 Reviewer 检查。

对 B 组这类安全审计任务，当前路线已经比较契合比赛目标：

- 低 token 传递 StateRef / MemoryRef。
- 非文本状态通过 Prompt View / Audit View 分层读取。
- ClaimCard 和 Evidence Ref 支撑最终审计链。
- Final Schema 保证最终输出可追溯、可审计、可交付。

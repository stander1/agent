# v5.13s 动态能力画像与能力动作视图

## 1. 本轮解决的问题

v5.13r 的最小上下文视图仍把协作职责归纳为 Planner、Writer、Reviewer 和 General 四类。该实现可验证“不同接收者读取不同上下文”，但不满足最终创新方案对任意 Agent 名称、任意角色说明和动态工具绑定的要求。

v5.13s 按最终版《低开销通信 v4》中的 Capability Profile Manager、Tool-Capability Synchronizer、Capability Router 和 Cold Start Tie Resolver，以及《非文本状态传递 v3》中的 Prompt View Renderer，补成以下通用链路：

```text
真实框架 Agent
  -> 动态发现名称、职责说明、系统提示词、工具和输出类型
  -> 三来源能力画像
  -> 语义动作识别
  -> 能力/动作决定最小信息字段
  -> State Access API 生成接收者专属 Prompt View
  -> 执行结果反向更新成功率、成本和 Schema 稳定性
```

核心代码不认识 Question A，也不要求开发者使用 planner、writer、reviewer 等固定名称。

## 2. Capability Profile Manager

每个实际发现的 Agent 都建立版本化能力画像，来源严格分开：

1. `role_capabilities`：从 Agent 名称、角色说明和系统提示词规则提取，来源为 `role`。
2. `tool_capabilities`：从已绑定工具的说明、能力标签和支持动作生成，来源为 `tool:<tool_id>`。
3. `runtime_capabilities`：根据真实执行动作及成功或失败结果更新，来源为 `runtime`。

画像同时记录：

```text
profile_version
preferred_actions
input_preference
output_types
available_tools
accepted_state_types
message_types
schema_reliability
history_success_prior
average_cost_tokens
average_latency_ms
current_load
memory_locality_count
```

冷启动成功率使用 Beta(1,1) 中性先验：

```text
(success_count + 1) / (success_count + failure_count + 2)
```

因此新 Agent 的 `history_success` 为 0.5，表示未知，不表示失败。

## 3. Tool-Capability Synchronizer

AutoGen Driver 在每次真实 Agent 调用前重新读取当前工具集合。新增工具后，系统自动加入工具能力、支持动作和成本等级；移除工具后，重新构建工具来源，只删除来自该工具的能力，不影响角色来源和运行时来源。

工具集合变化时 `profile_version + 1`；完全相同的重复注册不会制造无意义版本。工具能力的审计来源保留为 `tool:<tool_id>`，可说明某项能力为何存在。

## 4. Capability Router 与冷启动解析

规则路由采用最终方案中的公式：

```text
RouteScore =
0.45 * action_match
+ 0.35 * capability_match
+ 0.10 * tool_match
+ 0.10 * history_success
- 0.15 * cost_penalty
- 0.10 * schema_unreliability_penalty
```

同类资源平局不调用 LLM，而按以下顺序解决：

```text
能力专用度
必要工具可用性
记忆局部性
当前负载
Schema 稳定性
成本水平
确定性哈希
```

只有动作不在动态路由表、候选 Agent 无法覆盖所需能力，或高分候选的能力类型不同等语义不确定情况，才产生 `planner_fallback_required`。此时系统按 `task_decomposition`、`routing`、`orchestration` 能力动态寻找规划型 Agent，不依赖 Agent 名称中是否包含 `planner`。

在框架无关 Runtime 的 `active` 模式中，路由器可以采用建议接收者；在 AutoGen 的 `advisory` 模式中，AgentLite 只记录 `recommended_receiver`、候选分数和兜底原因，保留 AutoGen 对发言顺序和团队调度的所有权。

## 5. 动态能力/动作上下文视图

生产链路不再先把 Agent 映射成固定角色。视图输入改为：

```text
consumer_id
profile_version
capabilities
preferred_actions
input_preference
output_types
accepted_state_types
current semantic_action
current user task
admitted MemoryView / StateRef
```

系统先识别本次调用动作，例如 `RETRIEVE_EVIDENCE`、`WRITE_OUTPUT`、`REVIEW_OUTPUT`、`RUN_CODE`，再结合能力画像推导本次真正需要的信息字段。一个同时具备检索和审查能力的 Agent，在检索调用和审查调用中会得到不同视图，不会因 Agent 名称固定成一种角色。

State Access API 同样使用能力和动作决定视图：

1. 调度、路由类动作默认只读元数据。
2. 检索、证据验证类动作读取排序和去重后的证据片段。
3. 写作、综合、编码类动作读取有限必要片段。
4. Full-read 仍只用于显式升级、调试或特殊任务。

连续任务明确引用前序信息而最小视图缺字段时，系统仍按字段从来源状态受限补取；不会把完整历史广播给所有 Agent。

## 6. AutoGen 接入行为

Driver 从 AutoGen 实例动态读取：

```text
name / id
description
system messages
metadata capability declarations
bound tools and handoff tools
output type
team participants
```

Team 改写包为每个真实接收者保存独立的 `context_profile`。Agent 调用前只水合匹配自己的分区，标记为：

```text
AGENTLITE_RECEIVER_CAPABILITY_VIEW v1
```

其中包含 `consumer_id`、`semantic_action`、`capability_profile_version`、`capabilities` 和 `information_fields`。v5.13r 的 `semantic_role` 只在解析历史归档时兼容，当前生产写入路径不再生成该字段。

## 7. 可观测性

Trace、Pool Snapshot、会话报告和监控页新增或接入：

```text
capability_profile_updated
capability_profile_execution_started
capability_profile_feedback
registered_capability_profile_count
capability_context_view_count
capability_action_counts
current_load
memory_locality_count
recommended_receiver
planner_fallback_required
planner_fallback_reasons
```

运行反馈记录成功数、失败数、Schema 成功或失败、Token 成本和耗时，下一次路由会使用更新后的画像。

## 8. 兼容边界

`infer_collaboration_role()` 和 `build_minimal_role_view()` 仍保留为旧版测试与第三方调用兼容适配器，但 AutoGen 接管、State Access 和当前任务/记忆视图生产路径均不再调用它们。

本轮没有把 AgentLite 变成 AutoGen 的强制调度器，也没有新增领域规则。开发者可继续任意命名 Agent、任意组织 Team；提供清晰职责说明、工具元数据或能力声明时，画像会更准确，缺少声明时使用规则推断和运行反馈逐步更新。

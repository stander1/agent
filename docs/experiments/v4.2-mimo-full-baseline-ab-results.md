# v4.2 MiMo baseline 与 A/B 正式对比实验

日期：2026-06-21

## 实验目的

DeepSeek 本轮成本较高，并且大量请求未命中缓存。因此本轮切回 MiMo，重新运行 baseline 与 A/B 两组连续任务，判断在同一 provider 下 runtime_lite 对 token 与延迟的控制效果。

本轮运行模式：

- `baseline_text`：完整自然语言历史交接，对照组。
- `runtime_lite`：SHP + 状态池 + 记忆池 + 异步记忆准入，实验组。

## Token 口径说明

`llm_prompt_tokens`、`llm_completion_tokens`、`llm_total_tokens` 来自 provider 返回的 usage，是更接近后台账单的 token 数。

## 结论

在 MiMo 下重新运行 baseline 与 A/B 后，runtime_lite 同时降低了 token 与延迟。

最关键的结果是：A+B 合计 `llm_total_tokens` 从 4,398,786 降到 235,011，下降 94.66%；总延迟从 2,271,031ms 降到 1,734,706ms，下降 23.62%。这说明系统不是只减少了显式消息 token，而是在同一 provider 下真实减少了模型调用账单 token，并且延迟也随之下降。

延迟下降没有 token 下降那么夸张，原因是两组都仍然串行调用 5 个 Agent，每个任务仍有 5 次 LLM 请求。runtime_lite 主要减少了每次请求的上下文长度，但尚未减少必须串行等待的 LLM 调用次数。因此后续优化时间开销时，重点应放在调度层：减少串行 LLM 步数，或者让非 LLM 的规则校验、记忆候选判断、质量检查与下一步 Agent 调用重叠执行。

同时，runtime_lite 的后台记忆等待只有 0.1ms 量级，不构成延迟瓶颈。新增的记忆读取 token 也远小于 baseline 的完整历史上下文 token，说明没有出现明显的 cost shifting。

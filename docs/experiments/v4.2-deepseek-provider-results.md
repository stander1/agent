## 实验目的

本轮仍然只运行 `runtime_lite`，不重新运行 baseline。

## 结论

DeepSeek 本轮同样保持协议稳定：A/B 都是 100% 成功，`fallback_count` 为 0，最终交付字段完整，后台记忆任务全部完成且没有错误。

但是 DeepSeek 没有降低运行时间，反而比 MiMo v4.2 更慢：A 组增加 53.92%，B 组增加 33.36%。同时 DeepSeek 的 completion token 明显更多，A 组增加 62.03%，B 组增加 43.55%，说明不同 provider 的输出风格会显著影响端到端时间和 token 成本。

这轮结果支持一个更稳的判断：v4.2 运行时间主要由外部 LLM 调用耗时和模型输出长度支配，而不是后台记忆准入造成。后台记忆等待时间仍然只有毫秒级，A 组 0.875ms，B 组 2.844ms。

因此后续若要优化时间开销，重点应放在：

- 减少必须串行等待的 LLM 调用数量。
- 限制最终输出之前的中间 Agent 生成冗余，而不是限制最终交付物长度。
- 将规则校验、记忆候选判断、质量检查等非 LLM 步骤继续并行化。
- 记录不同 provider 的输出长度差异，避免把 provider 风格差异误判为运行时机制差异。

## 2. 总结结论

这次失败是真实失败，不是主指标统计错误：

| 指标 | Native | Managed | 变化 |
|---|---:|---:|---:|
| Provider 总 Token | 132,196 | 154,746 | 增加 22,550，增加 17.06% |
| 端到端协作 Token | 75,976 | 67,924 | 减少 8,052，降低 10.60% |
| 匿名综合质量均分 | 8.167 | 8.333 | 提高 0.167 |
| 完整交付数 | 5/6 | 5/6 | 持平 |

因此当前版本证明了：

1. AgentLite 已经真实改写 AutoGen 消息并降低了部分传输成本；
2. 综合质量没有下降；
3. 但 Provider 实际账单上升，端到端协作成本也未达到预注册的 15% 降幅；
4. 不能据此宣称系统已经实现稳定的低开销协作。

## 3. Provider Token 根因拆解

### 3.1 分场景结果

| 场景 | Native | Observed | Managed | Managed 相对 Native |
|---|---:|---:|---:|---:|
| A1-A3 旅行 | 86,198 | 73,652 | 70,832 | 降低 17.83% |
| B1-B3 合成审计 | 45,998 | 71,666 | 83,914 | 增加 82.43% |

总结果被 B 组完全反转。A 组表面上达标，但三组发生第二轮
Planner/Writer/Reviewer 的任务并不相同，因此不能把 A 组的全部降幅直接归因于
AgentLite。

### 3.2 同调用位置归一化

原比较器存在一个诊断字段兼容缺陷：

```text
llm_usage.jsonl 实际字段：
prompt_tokens / completion_tokens / total_tokens

比较器原先只读取：
llm_prompt_tokens / llm_completion_tokens / llm_total_tokens
```

这导致归一化结果被错误记录为 0。该缺陷不影响主 Provider 总数和预检失败结论，
但会隐藏根因。修复后，按 `task_id + agent + Agent 内调用序号` 配对得到：

| 场景 | Native 配对 Token | Managed 配对 Token | 变化 |
|---|---:|---:|---:|
| A | 52,631 | 51,546 | 降低 2.06% |
| B | 45,998 | 59,998 | 增加 30.44% |
| 合计 | 98,629 | 111,544 | 增加 13.10% |

其中 B 组相同调用位置的 Prompt Token 从 30,094 增加到 43,557，增加
44.74%。这说明问题不仅来自额外轮次，单次 LLM 输入本身也明显膨胀。

### 3.3 额外轮次

B2 的 Managed 运行发生了第二个完整的
`Planner -> Writer -> Reviewer` 周期：

```text
相同调用位置额外成本：14,000 Token
Managed 额外三次调用：23,916 Token
B 组总增量：37,916 Token
```

合并 A/B 后，Managed 相对 Native 的 22,550 Token 增量可拆为：

```text
相同调用位置增量：12,915 Token
额外/不匹配调用增量：9,635 Token
```

因此约 57% 的总增量来自相同调用位置的上下文膨胀，约 43% 来自轮次结构和
生成波动。不能只通过限制轮次掩盖问题。

Observed 的 B 组同样出现额外三次调用，且总 Token 比 Native 高 55.80%。
这证明单次真实模型运行存在明显方差。正式实验必须进行独立重复并报告离散程度。

## 4. 端到端协作成本

Managed 的 67,924 个端到端协作 Token 构成为：

| 分量 | Token | 占比 |
|---|---:|---:|
| 直接消息 | 22,473 | 33.09% |
| Prompt View | 39,691 | 58.44% |
| 记忆读取 | 5,760 | 8.48% |
| 控制 LLM | 0 | 0% |
| 重试 | 0 | 0% |

主要成本已经从直接消息转移到 Prompt View。当前结果属于“部分减少直接通信，
但视图重建仍过重”，尚未形成稳定的端到端成本下降。

分场景看：

- A：39,328 -> 32,167，降低 18.21%；
- B：36,648 -> 35,757，仅降低 2.43%。

B 场景是下一阶段的首要定位对象。

## 5. 质量审计

综合均分不低于 Native，但聚合结果掩盖了局部回退：

| 任务 | Native | Observed | Managed | Managed 完整交付 |
|---|---:|---:|---:|---|
| A1 | 5 | 8 | 8 | 是 |
| A2 | 8 | 5 | 8 | 是 |
| A3 | 8 | 8 | 8 | 是 |
| B1 | 8 | 10 | 10 | 是 |
| B2 | 10 | 10 | 6 | 否 |
| B3 | 10 | 4 | 10 | 是 |

B2 的 Managed 最终输出经历了两个完整协作周期，并非被 `max_turns` 截断。
它的问题是：

1. Reviewer 输出成了批量“验收报告”，而不是用户要求的 `retrieval_state` 摘要；
2. 最终文本混入了 B1 阶段的下一步动作，说明历史产物进入当前角色视图过多；
3. 本地交付 Guard 判为有效，但盲测技术裁判判为不完整，说明通用本地 Guard
   不能替代独立质量评审。

下一版质量门禁除聚合均分外，还必须增加：

```text
Managed 不得出现 Native 没有的阻断级失败；
每个任务的 Managed 分数不得相对 Native 下降超过预注册边界；
最终交付类型必须匹配当前用户请求，而不是只验证文本非空或字段存在。
```

这些规则用于下一次预注册，不能回头修改本次实验结论。

## 6. 记忆与角色视图问题

### 6.1 A 场景

- 正式记忆：1；
- MemoryView：1；
- 唯一记忆读取 Token：664；
- 向多个接收者展开后的 Token：2,688；
- 扇出倍率：约 4.05 倍；
- 三次注入均为 `unassessed`，没有被确认实际支持最终输出。

### 6.2 B 场景

- 正式记忆：11，但按摘要只有 7 种不同内容；
- MemoryView：8，但按 Prompt 摘要只有 5 种不同内容；
- 66 个 Claim Candidate 按当前可见语义只有 27 种不同内容；
- `memory_candidate_deduplicated_count=0`，说明现有去重没有捕获这些重复项；
- `alert_id`、`proxy_token`、`device`、`wallet`、映射来源和下一跳实体均落入
  `slot.runtime.config`，槽位语义过粗。

同一段完整报告被分别挂到多个字段值上，随后又进入 Planner、Writer、Reviewer
视图。这违反了最终创新方案中的“MemoryView 归并去重”和“业务 Agent 默认读取极简
Prompt View”原则。

下一版应按稳定 `semantic_key + slot_id + scope + normalized_value` 去重，并让每个
MemoryView 行只携带自己的 `active_value`、最短证据摘要和引用；完整报告保留在
Audit/Storage View，不进入每个业务 Agent 的 Prompt View。

## 7. StatePool 问题

报告记录了 166 个 `artifact_state`、878,937 字节，但进一步核查发现：

- 83/166 是 AutoGen 的 `DefaultTopicId`、`AgentId` 等路由元数据；
- 按审计载荷真实 SHA-256 去重，A、B 各有 20 条重复内容，共 40 条；
- 重复内容约占全部状态行的 24.10%；
- 当前没有真实 `retrieval_state`；
- 当前没有真实 `embedding_state`。

因此“166 个结构化非文本状态”只能证明结构化 artifact 包装路径工作，不能作为
比赛最终所需的三类非文本状态证据。路由元数据应留在 trace，不应默认注册为业务
`artifact_state`；相同载荷应复用同一个 state_id 或增加引用计数。

这与最终创新方案的“状态池不是无限日志库”“状态去重”“机器状态与 Prompt View
分离”要求一致。

## 8. 协议标记泄漏

B1 的 Managed 最终 Reviewer 文本出现：

```text
[writer] AGENTLITE_REAL_REWRITE v1
```

Writer 的用户可见输出本身没有该标记。泄漏发生在 Reviewer 接收内部改写消息时：
内部传输包装被当成上游正文的一部分，Reviewer 随后在最终报告中引用了它。

下一版必须在构造 Agent 可见角色视图前解包内部传输信封，只把业务 Prompt View
交给模型；`AGENTLITE_*` 标记、`shp_wire` 和状态池迁移字段只能存在于运行时元数据、
trace 或 Audit View。

## 9. 下一阶段：v5.14c

建议将下一阶段定为“最小充分上下文与证据卫生”，按以下顺序实施：

1. 修复归一化比较器字段兼容问题，并增加真实 Provider 字段回归测试；
2. 在 StatePool 写入前过滤纯路由元数据，对相同审计载荷做内容寻址去重；
3. 修复 Memory Candidate、Claim Card、MemoryView 的语义去重和槽位归一；
4. 将完整历史报告移出业务 Prompt View，只注入当前任务所需字段；
5. 对同一任务的共享事实只构建一次，再按动态能力画像生成最小接收者视图；
6. 解包并清除所有内部协议标记，禁止其进入 LLM 可见正文和最终输出；
7. 增加逐任务质量非劣门禁、协议泄漏门禁、状态有效载荷占比和重复率指标；
8. 重新运行 A1-A3/B1-B3，至少完成两次独立重复后再决定是否扩到十轮。

本阶段不通过缩短最终答案或人为限制 completion Token 获得降幅。

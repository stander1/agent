## 3. 真实根因

### 3.1 Reviewer 成果所有权混乱

多项 Managed 最终结果来自 `reviewer_artifact`。Reviewer 本应验收 Writer，
却重新摘要或改写了成果：

- 修订清单带“最终可交付成果”标题后被误交付；
- 验收评估报告替代了当前任务要求的结构化成果；
- Reviewer 重写前序结论时引入新的事实冲突。

这不是固定角色名称问题，而是“验证者是否拥有成果重写权”的协议问题。
正确边界是：

```text
存在问题 -> Reviewer 否决并返回修订清单，不结束；
成果合格 -> Reviewer 按引用批准，运行时晋升原成果；
Reviewer 不重复传输、不摘要改写业务成果。
```

### 3.2 明确结论没有进入类型化共享记忆

共享记忆保存了大量 `slot.runtime.config` 配置事实，却没有识别
“综合风险判断：needs_more_evidence”这类明确结论。后续 Agent 因此只能
看到旧配置与模糊摘要，在最终整合时把已确认结论改成相反结果。

修复必须识别通用的“最终/当前/综合结论、判断、判定、决策、结果、状态”
及英文等价标签，写入 `slot.system.design_decision` 的类型化 scope；不能
硬编码具体结论值、领域实体或任务编号。

### 3.3 守卫对交付标题信任过强

旧守卫只在存在审查标题时稳定识别修订要求。若 Reviewer 第一行写
“最终可交付成果”，随后正文再声明“当前产出仅为修订说明、请重新生成”，
交付标题会掩盖真实语义。守卫应以正文是否闭环为准，标题不能覆盖缺失和
继续修订信号。

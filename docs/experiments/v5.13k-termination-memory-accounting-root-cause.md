# v5.13k 终止协议、记忆准入与成本拆分根因修复

## 1. 修复范围

本轮基于 fair-20260719-153104 的原始归档进行本机离线回溯，不调用 LLM。修复范围包括：

1. AutoGen Team 最终交付终止条件。
2. Team 输出进入长期记忆前的准入条件。
3. Reviewer 审查意见识别的通用规则。
4. AgentLite 协作 Token 的互斥成本拆分。
5. 自定义模型客户端 Provider usage 的报告合并。
6. 普通开发者旅行实验的阶段化 Agent 提示词与统一轮次上限。

AgentLite 通用运行时没有加入 Question A 的目的地、预算或行程关键词。旅行领域提示词只存在于 experiments/ordinary-developer-autogen。

## 2. 根因一：交付状态在实验层与运行时层口径不一致

### 2.1 现场证据

管理组 A5 的最终输出是 Reviewer 修订意见，没有精确完成标记。实验程序使用以下条件判定失败：

- 最终来源必须是 reviewer；
- 最后一行必须精确为 FINAL_ANSWER_READY；
- 正文不能只是审查意见；
- 正文长度达到最低要求。

因此 A5 在 run_result.json 中是 task_failed。

但 AutoGen Driver 的长期记忆提升只调用了 assess_final_delivery，并传入 marker，却没有设置 require_marker=True。缺少标记本身不构成失败；同时旧审查正则没有覆盖“尚未达到标准、需 Planner 与 Writer 协同修订、修订指令”这一类措辞，导致同一文本被运行时判断为 validated_final_artifact。

随后 Driver 为它赋予：

- candidate_kind = autogen_team_final
- confidence = 0.86
- importance = 0.82
- coverage = 0.78

这些数值均越过规则准入阈值，最终生成长期记忆 mem_c460d154ad83。

### 2.2 形成链路

1. Reviewer 输出否决意见。
2. 实验层因缺少精确标记判定 task_failed。
3. Driver 运行时没有要求标记，误判为有效最终交付物。
4. 候选获得高置信度并被规则优先准入。
5. A6-A10 共检索 35 次，实际注入 Prompt 30 次。
6. 错误审查意见跨任务传播，形成记忆污染。

### 2.3 责任边界

这是 AgentLite 运行时缺陷，不是 Question A 评分规则导致的：

- 最终交付状态没有成为长期记忆准入的强前置条件；
- 文本正则被当成主要语义判断，而协议状态没有优先；
- 实验层和运行时层调用同一校验器时使用了不同参数。

### 2.4 通用修复

- AutoGen Driver 默认要求 Team 最终输出最后一行精确包含完成标记。
- 标记可通过 AGENTLITE_AUTOGEN_FINAL_MARKER 配置，默认 FINAL_ANSWER_READY。
- 没有精确标记的 Team 输出仍可进入候选审计记录，但只能以 autogen_team_unvalidated 和低置信度进入，不能写入长期记忆。
- 扩充通用 Reviewer 形态识别，覆盖“审查发现、尚未达到标准、修订指令、审查才会通过、需 Planner/Writer 修订”等领域无关表达。
- 增加无标记输出禁止长期记忆、伪装带标记审查意见禁止长期记忆的回归测试。

## 3. 根因二：严格终止组件存在，但实验没有接入

### 3.1 现场证据

项目已经实现 ReviewerFinalTextTermination，其语义是：

1. 只读取可见 TextMessage。
2. 只接受指定来源 reviewer。
3. 只接受最后一行精确标记。
4. 标记出现后仍执行规则优先交付校验。

但代码实验和 Studio Team 模板仍然使用 AutoGen 标准 TextMentionTermination。该组件只做字符串包含匹配，只要正文任意位置出现 FINAL_ANSWER_READY 就停止。

因此 Reviewer 在否决意见中讨论完成标记，也可能触发提前终止。实验归档中的 observed A6、A9、A10 和 managed A3 等任务出现了这类停止。

### 3.2 责任边界

这是实验接线缺陷，不是 AgentLite 底层消息改写导致的。三组都使用了同一个宽松终止器，因此原生组、观察组和管理组都会受到影响。

### 3.3 通用修复

- code_app.py 改用 ReviewerFinalTextTermination。
- Studio Team 模板改用同一可序列化组件。
- 三组仍然使用完全相同的终止组件，不改变公平实验边界。
- Reviewer 不通过时被明确要求不得输出或讨论完成标记。

## 4. 根因三：Agent 角色提示词与连续任务阶段不一致

### 4.1 现场证据

A1 只要求整理需求，A2 只要求三个候选地，A3 才要求初版行程，A5/A10 才要求完整手册。

旧 Writer 提示词要求每轮都输出“完整旅行方案”；旧 Reviewer 提示词又按“可直接执行的完整最终旅行方案”验收所有任务。于是阶段性成果会被当作不完整最终手册否决。

这解释了三组共同出现的质量地板：

- 28/30 最终输出只是 Reviewer 审查意见；
- 仅 1 份完整交付；
- 1 份空输出。

### 4.2 责任边界

这是实验团队配置缺陷，不是 AgentLite 通用运行时缺陷。

### 4.3 修复

旅行实验提示词调整为：

- Planner 先识别当前任务要求的交付物；
- Writer 交付当前阶段的完整成果，而不是每轮都生成最终手册；
- Reviewer 按当前阶段验收；
- 非关键资料允许使用透明、可修改的合理假设；
- 只有真正影响当前任务完成的缺失才构成否决理由。

这些规则只存在于实验目录，模拟普通开发者为旅游任务配置专业 Agent，不进入 agent_runtime。

## 5. 轮次问题

旧实验使用 6 个 turn，即两个 Planner -> Writer -> Reviewer 周期。

六轮并不是造成全部失败的唯一原因，因为第二个 Writer 已经有一次根据 Reviewer 意见修订的机会；但当第二个 Reviewer 仍然否决时，任务会以审查意见结束。严格提示词和提前终止会进一步压缩有效修订空间。

本轮将默认和 Studio 模板统一为 9 turn：

- 最多三个完整周期；
- 有效最终答案仍可通过严格终止器提前结束；
- 三组轮次完全一致；
- 到达上限仍不合格时记录 task_failed，不自动追加隐藏修复调用。

这不是给管理组额外机会，而是修复三组共同的实验团队容量配置。

## 6. 根因四：直接消息成本包含了 Prompt View 和记忆

### 6.1 原实现

历史 autogen_agent_input_real_rewrite 事件记录：

- rewritten_input_tokens：整个改写后输入；
- prompt_view_tokens：其中的状态视图；
- retrieved_memory_tokens：其中的记忆视图。

解析器却把 rewritten_input_tokens 同时记为 direct_message_tokens。这样 direct_message_tokens 已经包含后两项；可视化若再次相加就会重复记账。

### 6.2 修复

新追踪事件显式记录 rewritten_wire_tokens。对于旧追踪，解析器使用残差回算：

direct_message_tokens =
runtime_tokens - prompt_view_tokens - retrieved_memory_tokens

三项成为互斥口径：

direct_message_tokens + prompt_view_tokens + retrieved_memory_tokens
= end_to_end_collaboration_tokens

### 6.3 原归档回放结果

修复前：

- runtime = 46,042
- direct_message = 46,042
- prompt_view = 11,800
- memory = 18,210

修复后：

- runtime = 46,042
- direct_message = 16,032
- prompt_view = 11,800
- memory = 18,210
- 三项合计 = 46,042

总传输量和 79.7651% 节省率没有变化，变化的是成本构成标签变得正确。

## 7. 根因五：自定义模型客户端绕过 AutoGen usage hook

代码实验为兼容 MiMo 使用自定义 OpenAICompatibleClient，并直接通过 urllib 请求 Provider。AgentLite 能接管 AutoGen 协作消息，但 AutoGen model_client hook 看不到这类自定义 HTTP 客户端，因此 Session 报告中的 llm_* 为 0。

这不是 Token 未统计，而是两份遥测没有合并：

- 实验程序的 llm_usage_summary.json 有真实 Provider 用量；
- AgentLite trace 有协作传输用量。

修复后 agentlite report autogen-session 支持：

--provider-usage path/to/llm_usage_summary.json

当 AutoGen model_client hook 没有 LLM 用量时，报告使用外部 Provider usage 文件补齐；若 hook 已有数据，则不重复相加。

用原管理组归档回放后：

- llm_usage_source = external_provider_usage_file
- llm_call_count = 57
- llm_total_tokens = 881,694

## 8. 验证结果

本机使用已有 agentlite-autogen Conda 环境和 AutoGen 0.7.5：

- Python 编译检查：通过
- 重点回归测试：46 项通过
- 完整测试集：163 项通过
- Studio Team 自定义终止组件反序列化：通过
- 原始 managed 归档重新生成报告：通过
- Provider usage 合并：57 次调用、881,694 Token
- 成本互斥校验：16,032 + 11,800 + 18,210 = 46,042

验证过程没有调用外部 LLM。

## 9. 下一步实验门槛

不要直接重跑 A1-A10。先运行三组 A1-A3 冒烟测试，并检查：

1. Reviewer 否决意见不会触发完成终止。
2. 未带精确标记的 Team 输出不会进入长期记忆。
3. A1 最终交付是需求清单，A2 是三个候选比较，A3 是初版行程。
4. AgentLite 报告中的三项传输成本严格相加等于运行时总传输。
5. 使用 --provider-usage 后，报告 LLM Token 与 llm_usage_summary.json 一致。
6. 三组使用相同模型、温度、9 turn 上限、Agent 提示词和终止组件。

只有 A1-A3 通过，才进行新的 A1-A10 三次重复正式实验。

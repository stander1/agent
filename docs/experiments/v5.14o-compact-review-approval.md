# v5.14o 紧凑 Reviewer 审批语义

## 1. 真实失败

v5.14n（实验编号 `20260727-163802`）完成了 60 个候选任务和全部评分，
但阶段验收仅通过 `279/316`。接管组只有 2 次成果引用晋升，出现 14 次
Reviewer 审批正文替代业务成果；A 组所有候选的最终正文几乎都只剩
“验收通过/批准上一份 Writer 成果”。

失败归档 SHA-256：
`7b3d742eff17f69e9e20ff20991dcde8ee594547b98fbdb7755f41c6435ff762`。

## 2. 根因

旧规则支持“前序、此前、上一版、上轮、previous、prior”等引用词，
但没有覆盖“上一份、前一份、最近一份”。同时，短语“验收通过”没有
携带显式成果名时，也不会被识别为审批。

于是 Reviewer 短文被当作自己的合法成果，`final_resolution_kind` 变成
`reviewer_artifact`，真正的业务正文没有被晋升。

## 3. 通用修复

1. 引用词补充“上一份、前一份、最近一份”；
2. 对不超过 600 字、从验收/审查/审核/评审通过或英文 approved 开始的
   紧凑审批短文，按引用审批处理；
3. 仍要求最近候选成果通过当前任务的完整交付守卫；
4. 无候选、修订反馈、验收不通过均不能晋升；
5. 紧凑审批后出现完整业务正文时不按审批短文处理。

该修复只解释协作协议语义，不认识 Question A/B、旅游或安全审计实体。

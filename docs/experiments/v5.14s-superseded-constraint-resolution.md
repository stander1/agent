# v5.14s Superseded Constraint Resolution

## Evidence that triggered this stage

The v5.14r formal run preserved the complete current candidate for every
validation receiver (`29/29`), but the A terminal artifact was rejected as a
numeric upper-bound violation. The candidate's current total was below the
active bound; a larger value appeared only in its required decision history.

## Root cause

The rules-first final-delivery guard treated every clause containing the word
`budget` as a current total assertion and selected the largest monetary value
from that clause. This conflated three distinct semantics:

1. the active upper bound;
2. the current executable total;
3. superseded values retained for auditability.

The reviewer correctly approved the candidate, but artifact promotion rejected
it and exposed the compact approval text as the final answer.

## Generic correction

The guard now:

- evaluates explicit total expressions rather than every budget mention;
- ignores numbered historical record clauses as current totals;
- evaluates the replacement side of explicit transitions such as
  `reduced from X to Y`;
- ignores quantities locally attributed to initial, original, previous, or
  former budgets;
- continues to reject a replacement or current total above the active bound.

This mechanism is independent of Question A/B, application domain, language,
and agent role names.

## Acceptance

`experiments/v5.14s-superseded-constraint-resolution/run_openeuler.sh` runs the
full unit suite and a focused mechanism report on openEuler, then packages
immutable evidence with a SHA256 checksum.

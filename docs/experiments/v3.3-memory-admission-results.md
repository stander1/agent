# v3.3 Memory Candidate Admission Lite Results

## Positioning

This is a v3 internal completion, not a new mainline innovation route.

It implements the TLC-Memory path required by the innovation plan:

```text
Contract Guard control.memory_card / claim_cards
  -> Memory Capture Layer
  -> MemoryCandidate / ClaimCandidate
  -> Memory Admission Lite
  -> admitted candidates only
  -> MemoryStore / ClaimCard / MemoryView
```

Before this change, `runtime_lite` wrote Writer / Reviewer / MemoryManager output
directly into `MemoryStoreLite`. That made the prototype easy to run, but it did
not fully match the planned candidate/admission lifecycle.

## Implemented Scope

- Added `MemoryCandidate`, `ClaimCandidate`, and `MemoryAdmissionReport`.
- Added rule-first admission states:
  - `admitted`
  - `rejected`
  - `pending`
  - `audit_only`
  - `unresolved_slot`
- Changed `runtime_lite` Contract Guard path so `memory_card` and `claim_cards`
  are captured as candidates first.
- Only `admitted` candidates update `ClaimCard`, `MemoryView`, and `MemoryRef`.
- Preserved the old direct write path only for deterministic compatibility when
  no Contract Guard metadata exists.
- Added admission observability:
  - `memory_candidate_count`
  - `claim_candidate_count`
  - `memory_admitted_count`
  - `memory_rejected_count`
  - `memory_pending_count`
  - `memory_audit_only_count`
  - `admission_unresolved_slot_count`
  - `claim_to_memoryview_count`
  - `memory_admission_rate`

## Admission Rules

The v3.3 admission gate is intentionally lightweight and deterministic.

```text
unresolved slot        -> unresolved_slot, do not update MemoryView
empty summary          -> rejected, do not update MemoryView
confidence < 0.35     -> rejected, do not update MemoryView
high loss + raw needed -> audit_only, do not update MemoryView
weak confidence/import/coverage -> pending, do not update MemoryView
otherwise             -> admitted, update MemoryStore / ClaimCard / MemoryView
```

This keeps v3.3 aligned with the original scheme: `memory_card` is not the final
long-term memory object. It is only an input to the candidate/admission layer.

## Interpretation

The smoke result confirms that runtime memory creation now passes through the
candidate/admission layer before it reaches `MemoryView`.

The A1 smoke is not a quality comparison. It only verifies the lifecycle
mechanism on a low-cost task. A full A/B rerun can be done after v3.3 is tagged,
but the main validation for this step is structural:

```text
memory_candidate_count == 3
memory_admitted_count == memory_write_count == 3
claim_to_memoryview_count == 3
schema_valid_rate == 1.0
```

This means the v3 line now has the missing TLC-Memory admission gate and can move
to v4 lifecycle/cost-control work without leaving `direct-to-MemoryStore` as an
architectural hole.

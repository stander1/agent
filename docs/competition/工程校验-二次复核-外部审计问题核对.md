## 2. 总体修正结论

外部审计报告的核心警告是成立的：当前工程不能被描述为“三份最终创新方案已经基本完整实现”。更准确的定位应该是：

> 当前工程已经实现了比赛原型的可运行骨架和若干 Lite 闭环，但距离最终方案中的完整运行时系统还有明显缺口。

上一份 `工程校验-方案规划与实现对照.md` 中“整体方向一致、没有方向性冲突”的判断仍然成立，但“已对齐”的措辞偏宽。很多模块应该改成：

- Lite 对齐；
- 部分实现；
- 未实现完整机制；
- 仅有指标观测，没有形成控制器。

外部审计报告也存在若干过度判定：它把一些已经存在的 Lite 机制写成“完全未实现”，例如：

- State-to-Memory 路径并非完全没有；
- SHP-lite 包并非完全没有；
- Read Lease-lite 并非完全没有；
- Tombstone-lite 并非完全没有；
- v4 成本统计并非只有空指标。

所以最终判断不是“完全符合”，也不是“全部推倒”，而是：

> 当前工程是一个能跑实验的 Lite Runtime；P0 级核心缺口必须补齐，否则比赛答辩时不能声称完整实现三大创新方案。

## 3. 外部审计中确认成立的问题

### 3.1 AutoGen / 跨框架适配未实现

结论：成立。

当前 `docs/competition/比赛报告骨架.md` 已经把系统定位为 AutoGen / CrewAI / LangGraph 上层框架之外的运行时通信层，但代码中还没有 `agent_runtime/adapters/`，也没有实际 AutoGen baseline 或 adapter 实验。

影响：

- 如果直接答辩“跨框架运行时层已完成”，证据不足。
- 当前只能说“核心 runtime 机制已具备，后续可通过 adapter 接入 AutoGen 等框架”。

建议：

- AutoGen 可以后移，但接口设计必须从现在开始按可适配方式整理。
- 先补稳定内核，再接 AutoGen 是合理路线。

### 3.2 SHP 协议包只有 lite 版本，不是最终规范

结论：成立，但不是“完全未实现”。

`runtime.py` 中存在 `_build_shp_message()`，字段包括：

```text
shp_id
protocol_version = v1-lite
from
to
task_id
action
summary
parameters
state_refs
memory_refs
```

这说明 SHP-lite 已实现。

但最终方案要求更完整的协议包，例如：

```text
header
control
summary
state_refs
memory_refs
metrics
routing
access_policy
protocol_version
```

当前缺少：

- 明确的 `header/control` 分层；
- 通信成本和状态访问 metrics 内嵌；
- message type 枚举；
- access policy / readiness 状态；
- router 可读的 capability hint。

建议：

- 下一步应实现 `SHPEnvelope` 数据结构，而不是继续拼普通 dict。

### 3.3 Typed Artifact Digest 只是通用摘要，不是类型感知摘要

结论：成立。

`contract_guard.py` 的 `build_artifact_digest()` 只区分：

```text
json
natural_language
```

并记录：

```text
detected_headings
summary
content_hash
content_chars
```

这不是最终方案中的 Typed Artifact Digest。最终方案要求按产物类型差异化摘要，例如：

- Python 代码：函数签名、导入、类名、入口函数；
- JSON：schema、顶层 key、字段类型；
- terminal log：exit_code、错误模式、关键 traceback；
- CSV / table：列名、行数、缺失值、样例行；
- Markdown 文档：标题树、关键决策、证据链。

影响：

- 现在 digest 可以辅助 retry，但不能充分支撑 Memory Admission、Cold Access、摘要质量门控。

建议：

- 优先补 `TypedArtifactDigestBuilder-lite`，这是高性价比补强。

### 3.4 Batch Compaction Engine 未实现

结论：成立。

当前 `MemoryStoreLite` 的 `_upsert_memory_view()` 会把同 slot 的 claim 汇总到 MemoryView，并用 `_compact_claims()` 拼接最近 4 条 summary。

但这不是 Batch Compaction Engine。

缺少：

- 显式 `run_compaction()`；
- compaction 触发条件；
- compaction log；
- old claim 到 new MemoryView 的可追溯映射；
- 批量合并策略；
- 合并后的冲突处理；
- compaction metrics。

影响：

- TLC-Memory 的“生命周期治理”展示力不足。

建议：

- 实现规则版 `run_compaction()`，先不调用 LLM。

### 3.5 Semantic Schema Registry / CCF 仍是简化版

结论：成立。

当前代码有：

- `CANONICAL_SLOTS`
- `ALIAS_MAPPING`
- `ClaimCard`
- `ClaimCandidate`

这是 v3.1/v3.3 的必要补强，但还不是完整 SSR/CCF。

缺少：

- registry 对象；
- slot metadata；
- conflict_policy；
- temporal / scope required；
- prompt rendering policy；
- embedding similarity matching；
- Canonical Claim Form 的 `claim_type`、`polarity`、`modality`、`temporal_scope`、`schema_version` 等字段。

建议：

- 不需要一步到位做动态注册，先做 `SchemaRegistryLite`，把现在的常量提升成结构化配置。

### 3.6 Conflict Resolver 未实现

结论：成立。

当前 `_upsert_memory_view()` 会把同 slot 的 active claim 放进同一个 view，但没有真正判断冲突。

缺少：

- per-slot conflict policy；
- last_write_wins；
- highest_confidence；
- merge；
- manual_review；
- unresolved_conflict 状态触发。

影响：

- 记忆会聚合，但不具备“治理冲突”的能力。

建议：

- 先做最小 `ConflictResolverLite`：同 slot + 同 subject 下按 confidence / created_at 选择 active claim，其他标为 superseded 或 unresolved_conflict。

### 3.7 State GC / Read Lease / Tombstone 都只有 lite 版本

结论：成立。

当前 `StatePoolLite` 已有：

- `LeaseRegistry`；
- `active_readers`；
- `collect_garbage()`；
- `_tombstone_state()`；
- hot/warm/cold file-backed tier。

但最终方案要求的完整 Control-Flow-aware State GC 还远未实现。

缺少：

- dependency_ref_count；
- retry_ref_count；
- TTL / heartbeat / fencing token；
- crash recovery；
- DAG liveness；
- retry loop compaction；
- quota-based eviction；
- loop budget；
- tombstone 两阶段恢复；
- replacement_state_id / fallback_summary。

建议：

- 下一步先补 quota + lifecycle + replacement tombstone，不急着做完整 9 层 GC。

### 3.8 Cold Access Manager / Access Escalation / Readiness Barrier 未实现

结论：成立。

当前 state access 可以渲染 prompt view / audit view，但没有独立的：

- Cold Access Manager；
- raw span resolver；
- raw view cache；
- cold read queue；
- I/O budget controller；
- Access Escalation Governor；
- Readiness Barrier。

影响：

- 当前 runtime 可以避免传长文本，但还不能证明“按需升级读取 raw 冷数据”的完整成本控制链。

建议：

- 比赛版可先做 `ReadinessBarrier-lite` 和 `ColdAccessRequest-lite`。

### 3.9 非文本状态中的 embedding/vector 证据不足

结论：成立。

当前 `StateRef` 有：

```text
contains_embedding_refs
```

但 `_write_agent_state()` 写入所有状态时传入的是：

```text
contains_embedding_refs=False
```

`retrieval_state` 有 `chunk_ids`、`source_ids`、`score_map`、`evidence_rank`，但没有：

- `query_embedding_id`
- `chunk_embedding_ids`
- `vector_dim`
- `similarity_scores`
- vector backend / embedding store

影响：

- “非文本状态传递”容易被质疑为“把文本存到文件里再传 ID”。

建议：

- 先增强 retrieval_state，加 embedding metadata stub；后续再接真实 embedding。

## 4. 外部审计中过度或不准确的问题

### 4.1 “State-to-Memory Semantic Bridge 完全未实现”不准确

更准确结论：已有 Lite 路径，但不是最终方案的完整 Semantic Bridge。

当前路径是：

```text
_write_agent_state()
  → state_refs / evidence_refs
  → _schedule_runtime_memory_write()
  → _write_runtime_memory()
  → write_memory_candidate_with_report()
  → MemoryCandidate / ClaimCandidate
  → Admission
  → write_memory_with_report()
  → PromotionView / ClaimCard / MemoryView
```

已经具备：

- 状态引用进入记忆候选；
- evidence_refs；
- source_state_ids；
- MemoryCandidate；
- ClaimCandidate；
- Admission；
- PromotionView 记录。

但缺少：

- 独立 Promotion View Renderer；
- Memory Promotion Compiler；
- Semantic Validator；
- 不同 state_type 的 promotion 模板；
- 明确禁止 raw state 直接进入 memory 的工程边界测试。

所以应标为：

```text
Lite 已实现，完整语义桥未实现。
```

而不是：

```text
完全未实现。
```

### 4.2 “SHP 协议包完全未实现”不准确

更准确结论：SHP-lite 已实现，完整 SHP protocol 未实现。

当前 `_build_shp_message()` 已经生成 `shp_id`、`protocol_version`、`state_refs`、`memory_refs`。问题是结构不够完整，不是完全没有。

### 4.3 “Read Lease 未实现”不准确

更准确结论：Read Lease-lite 已实现，完整 Read Lease 协议未实现。

当前 `LeaseRegistry.read_lease()` 已经保护读取过程，并且 `collect_garbage()` 会检查 `active_readers`。

但它缺少 TTL、heartbeat、fencing token、crash recovery，所以只能用于单进程 lite 场景。

### 4.4 “Tombstone 完全未实现”不准确

更准确结论：Tombstone-lite 已实现，两阶段恢复和 fallback tombstone 未实现。

当前 `_tombstone_state()` 会写 tombstone JSON，并删除 payload。

缺少的是：

- logical evict 和 physical delete 分离；
- fallback_summary；
- replacement_state_id；
- StateUnavailable 处理；
- tombstone sweep。

### 4.5 “v4 仅有基础 metrics，缺联合成本公式”不准确

更准确结论：成本统计和报告已实现，但控制器未实现完整策略。

当前 `metrics.py` 和 `competition_report.py` 已经统计：

- direct message tokens；
- prompt view tokens；
- retrieved memory tokens；
- control LLM tokens；
- retry tokens；
- provider usage tokens；
- llm_total_tokens；
- fallback_count；
- schema_valid_rate。

外部审计说“只有基础 metrics”偏严格。真正缺的是：

- Access Escalation Governor；
- I/O Budget Controller；
- LLM Budget Controller；
- Readiness Barrier；
- 动态路由降低无效调用。

也就是说：

```text
成本观测已实现；
成本控制器未完整实现。
```

### 4.6 “web_monitor 完全未实现”要分本地版和提交版

当前工作区中存在 `web_monitor/`、`tests/test_web_monitor.py`、`tests/test_pool_snapshots.py`，但这些文件处于 untracked 状态，还没有提交到 Git。

因此：

- 对本地工作区：web_monitor 不是完全没有；
- 对 GitHub 当前提交版：web_monitor 仍可视为未交付。

这类判断必须区分“本地未提交代码”和“仓库已提交代码”。

## 6. 重新调整后的优先级

考虑用户希望暂缓 AutoGen，并先把整体工程做圆满，这个判断是合理的。新的建议顺序如下。

### v5.1：核心协议与桥接补齐

目标：

1. `SHPEnvelope` 正式结构。
2. `StateToMemoryBridgeLite` 独立模块。
3. `PromotionViewRenderer`。
4. `MemoryPromotionCompiler`。
5. `SemanticValidatorLite`。

意义：

先把三条创新线真正串起来，避免 state 和 memory 看起来只是松散拼接。

### v5.2：Typed Artifact Digest 与非文本状态增强

目标：

1. `TypedArtifactDigestBuilder-lite`。
2. code / json / markdown / log / table 多类型摘要。
3. `retrieval_state` 增加 embedding metadata。
4. 最小 `embedding_state`。

意义：

强化“非文本状态传递”和“低开销摘要”的答辩证据。

### v5.3：Memory Compaction 与 Conflict Resolver

目标：

1. `SchemaRegistryLite`。
2. `CanonicalClaimLite`。
3. `BatchCompactionEngine-lite`。
4. `ConflictResolverLite`。
5. `useful_memory_hit_rate`。

意义：

补齐 TLC-Memory 的核心生命周期治理，不再只是 memory search/write。

### v5.4：State Lifecycle / GC / Readiness Barrier

目标：

1. 状态生命周期状态机。
2. quota-based GC。
3. tombstone 两阶段化。
4. retry loop summary。
5. `ReadinessBarrier-lite`。

意义：

补齐 SHP-State 长任务和失败循环下的稳定性。

### v5.5：跨框架适配

目标：

1. AutoGen adapter。
2. AutoGen baseline。
3. AutoGen + runtime adapter 对比。

意义：

在核心接口稳定后，再做跨框架接入，减少返工。

## 7. 最终复核结论

外部审计报告中大约三类问题成立：

1. 完整创新机制确实缺口很大；
2. 当前实现大量是 Lite 版本；
3. AutoGen / openEuler / 完整比赛交付证据尚未完成。

但外部审计报告也有三类过度判断：

1. 把 Lite 实现说成完全没有；
2. 把成本观测缺口和成本控制器缺口混在一起；
3. 没有区分本地未提交代码和 GitHub 已提交代码。

因此，当前工程应重新定位为：

> 已完成 v0-v2 基础设施和 v3/v4 的 Lite 闭环；具备实验可运行性和初步成本优势；但 v5 前必须补齐核心协议、语义桥接、类型摘要、记忆压缩冲突治理和状态生命周期治理，否则不能声称完整实现最终创新方案。

## 2. 总体结论

当前工程已经实现了一个可运行的比赛版轻量原型，整体方向与三份最终版创新方案一致：以 `SHP-State` 做低文本状态传递，以 `TLC-Memory` 做跨轮记忆复用，以 `CMJCC` 做通信、记忆、控制成本的联合评估与治理。

但是，当前实现仍然是“比赛交付原型 / Lite 版本”，不是三份最终方案的完整研究型实现。最重要的差距有四类：

1. 跨框架适配层尚未真正落地。当前是框架无关的自研 runtime runner，还没有实际接入 AutoGen、LangGraph 等主流 Agent 框架。
2. 动态通信调度能力不足。最终方案中的 Capability Router、Communication Gate、Readiness Barrier 等机制，目前还没有形成完整调度闭环，当前主要是固定线性 Agent 流程。
3. 非文本状态传递已具备结构化形态，但 embedding/vector 相关状态还不够“硬”。当前有 `retrieval_state`、`artifact_state`、payload 引用、hash、审计 payload 等，但还没有真实 embedding 向量引用、向量维度、相似度分数和向量检索后端。
4. 记忆生命周期治理已经有候选池、准入、视图和 GC-lite，但 Semantic Schema Registry、Canonical Claim Form、冲突合并、批量压缩、成本敏感一致性控制仍是简化版。

因此，当前工程可以支撑比赛版答辩中的“原型系统 + 对比实验 + 工程可行性证明”，但如果要把论文方案完整讲成已经全部实现，需要谨慎措辞，应明确区分：

- 已实现：比赛版轻量机制。
- 部分实现：与方案同方向的 Lite 机制。
- 未实现：研究增强版和跨框架生产级能力。

## 4. 当前实现相对规划的主要偏差

### 4.1 最大偏差：跨框架适配还没有落地

我们之前确定的交付基调是“可适配多种 Agent 框架的低开销协作运行时层”。当前工程已经具备独立 runtime、状态池、记忆池、LLM 实验、评测报告，但还没有真正接入 AutoGen、LangGraph 或其他主流 Agent 框架。

这不影响当前实验用于证明机制可行，但会影响比赛交付物的说服力。因为第九题关注的是多智能体系统协作通信机制，如果最终只展示自研 runner，评委可能会认为系统通用性不足。

建议下一步优先做 `v5.1 AutoGen 最小适配层`，目标不是完整改造 AutoGen 底层，而是证明以下能力：

1. AutoGen Agent 原本要传长文本时，adapter 可拦截并写入 StatePool。
2. Agent 间实际传递的是 SHP + state_ref。
3. 下游 Agent 通过 State Access API 获取裁剪后的 Prompt View。
4. metrics hook 能统计原始 AutoGen baseline 与 runtime adapter 的端到端成本。

### 4.2 非文本状态传递已经有结构，但还需要更硬的证据

当前 `artifact_state` 和 `retrieval_state` 已经不是单纯的 `state_id`，而是包含 state type、payload kind、payload ref、hash、summary、audit payload 等信息。这已经符合“非文本/半结构化状态传递”的方向。

但最终方案中还强调 embedding、retrieval、artifact、task graph、execution graph 等多类状态。当前最弱的是 embedding/vector 相关状态：没有真实 `query_embedding_id`、`chunk_embedding_ids`、`vector_dim`、`similarity_scores`、vector backend。

建议比赛版至少补齐一个轻量 `embedding_state` 或增强 `retrieval_state`，字段可先采用本地 stub：

```json
{
  "state_type": "retrieval_state",
  "payload_kind": "structured_non_text",
  "contains_embedding_refs": true,
  "query_embedding_id": "emb_query_A01",
  "chunk_embedding_ids": ["emb_chunk_001", "emb_chunk_002"],
  "vector_dim": 384,
  "similarity_scores": [0.82, 0.77],
  "usage_hint": "summary_context_selection"
}
```

这样答辩时可以清楚说明：我们不是把文本存进数据库再传 ID，而是在 runtime 层传递结构化状态引用，下游按角色读取不同视图。

### 4.3 TLC-Memory 已经形成轻量闭环，但还不是完整生命周期系统

当前实现中，记忆不会直接由 Agent 输出写入长期池，而是经过候选、准入、视图、复用等过程。这与 `TLC-Memory` 的核心方向一致。

仍然不足的部分：

1. Semantic Schema Registry 还偏文档/轻规则，没有完整 registry 数据结构。
2. Canonical Claim Form 只是雏形，缺少标准字段、证据链、冲突状态和置信度更新。
3. Batch Compaction 和冲突合并没有完整实现。
4. `useful_memory_hit_rate` 这类质量型记忆指标还没有作为核心指标固化。

这些不一定阻碍比赛版，但需要在报告中说明“当前为 Lite 版”，并把未来增强路线写清楚。

### 4.4 CMJCC 的成本评估已比较完整，但动态通信优化还不完整

当前实现已经能记录和比较：

1. 直接消息 token。
2. Prompt View token。
3. 记忆读取 token。
4. 控制 token。
5. retry token。
6. provider 返回的真实 prompt/completion/total token。

这解决了“是不是把成本转移到记忆读取里”的质疑。

但低开销通信方案中另一个重要来源是动态避免无效通信，例如 Capability Router、Communication Gate、Readiness Barrier。目前这些还没有完全实现。因此当前实验主要证明“少传长文本 + 状态引用 + 记忆复用”带来的收益，尚未充分证明“动态路由减少无效 Agent 调用”的收益。

### 4.5 实验质量已改善，但还需要最终交付物质量证明

现有 v4.2 MiMo full baseline/runtime AB 结果已经显示 runtime_lite 在 token 和延迟上明显优于 baseline，且 `fallback_count` 为 0。这里的 `fallback_count` 指“降级兜底次数”：当模型输出无法按协议修复时，系统用 degraded message 保住流程不中断。它越高，说明协议稳定性越差。

但是比赛报告不能只展示 token 降低，还必须证明最终输出质量没有明显下降。当前 v5.0 已有报告生成器和规则质量门槛，但语义质量判断还偏弱。

建议补充：

1. 固化 A/B 最终交付物样例。
2. 增加 LLM judge 或人工 rubric，对完整性、可执行性、论证质量、格式合规性打分。
3. 报告中同时展示“成本下降”和“质量不下降/可接受”的证据。

## 5. 当前实现超出或不同于原规划的地方

### 5.1 Provider Guard 被独立出来是合理补充

最终方案重点讲的是 LLM 输出内容不合规时的 Contract Guard，但实际工程中还会遇到 HTTP 错误、provider response JSON 外壳异常、choices 缺失、content 为空等问题。当前实现把这部分独立为 Provider Guard，这是合理的工程补充。

需要注意边界：

- Provider Guard：处理服务商返回外壳异常。
- Contract Guard：处理模型正文内容不符合协议。

这不会违背创新方案，反而能让系统更稳。

### 5.2 异步记忆处理是合理补充

当前 runtime 中存在异步记忆准入/写入逻辑，让下游 Agent 执行和记忆候选处理可以并行。这符合用户之前提出的“规则操作和后续 Agent 可以并行”的方向，也符合低延迟目标。

需要注意的是，并行处理不能让 Memory Admission 绕过准入规则。只要候选、准入、写入长期记忆的边界仍然存在，就不违背 TLC-Memory。

### 5.3 当前三层状态池更偏工程实现，论文术语需要统一

工程中的 hot/cold tier、payload 文件、audit payload 与最终方案中的三层状态池概念方向一致，但命名和 API 边界还没有完全统一。报告中应避免说“完整实现三层状态池所有机制”，更稳妥的说法是：

当前实现了三层状态池的比赛版映射：

1. 热状态：当前轮次需要快速读取的 retrieval_state。
2. 冷状态：大文本 artifact_state 只保留引用和摘要。
3. 审计/工件状态：完整 payload、stdout/stderr/file/hash 等作为可追溯工件保存。

## 6. 建议的后续版本顺序

### v5.1：跨框架适配最小闭环

优先级最高。

目标：

1. AutoGen adapter 最小可运行 demo。
2. message interceptor：把长消息写入 StatePool。
3. SHP injector：向下游 Agent 传递 state_ref。
4. State Access API：下游读取裁剪 Prompt View。
5. metrics hook：比较 AutoGen baseline 与 runtime adapter。

意义：

这一步直接补齐“跨框架运行时层”的核心交付口径。

### v5.2：非文本状态证据增强

目标：

1. 增加 `embedding_state` 或增强 `retrieval_state`。
2. 补齐 vector_dim、embedding_id、similarity_scores、chunk_id、source_id 等字段。
3. 在报告中展示生成、传递、接收、使用流程。

意义：

这一步解决“是不是只是传数据库 ID”的答辩风险。

### v5.3：动态通信门控

目标：

1. 规则版 Capability Router。
2. 简化 Communication Gate。
3. ready/degraded/blocked 三态 Readiness Barrier。

意义：

这一步补齐低开销通信中“减少无效广播/无效 Agent 调用”的证据。

### v5.4：质量评估与最终报告固化

目标：

1. 固化最终 A/B 实验结果。
2. 引入 LLM judge 或人工 rubric。
3. 生成最终比赛报告 Markdown。
4. 生成图表：端到端 token、延迟、质量、fallback/schema、记忆命中。

意义：

这一步让比赛交付物从“系统能跑”变成“证据完整”。

## 7. 结论

当前工程和规划文档之间没有方向性冲突，三条主线都已经进入代码：

1. `SHP-State`：状态引用传递和非文本/半结构化状态池。
2. `TLC-Memory`：候选、准入、视图、复用的轻量记忆生命周期。
3. `CMJCC`：端到端成本拆分、协议守卫、重试、生命周期治理。

但当前实现与最终创新方案相比，仍存在明显 Lite 化：

1. 跨框架 adapter 未实现。
2. Capability Router / Communication Gate 未实现。
3. embedding/vector 状态证据不足。
4. Schema Registry / CCF / 冲突合并仍不完整。
5. 最终质量评估还需要更强语义证据。

因此，当前最准确的工程定位是：

> 一个已经跑通 A/B 实验、能证明低开销协作机制有效的比赛版运行时原型；它与最终创新方案方向一致，但还需要通过 v5.1-v5.4 补齐跨框架适配、非文本状态证据、动态通信门控和质量评估，才能更稳地支撑最终提交。

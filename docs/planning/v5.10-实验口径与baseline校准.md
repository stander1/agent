# v5.10 实验口径与 Baseline 校准

生成日期：2026-06-23

## 1. 背景

v5.9 重新实验已经证明 `runtime_lite` 在当前 A/B 连续任务下能显著降低 token 和延迟，但实验也暴露两个口径问题：

1. 现有 `baseline_text` 是全文广播滚雪球模式，适合作为压力测试，但不适合作为唯一主对照。
2. A10/B10 的最终输出存在交付物类型不一致：`baseline_text` 更像 Reviewer 审查报告，`runtime_lite` 更像最终手册正文，不能直接做公平质量裁判。

v5.10 的目标不是增加新机制，而是校准正式实验口径，让比赛报告更可信。

## 2. 采用的 Baseline 分层

正式报告采用三层实验对象：

| 名称 | 中文说明 | 作用 | 是否主对照 |
|---|---|---|---|
| `baseline_stress_full_broadcast` | 全文广播压力测试 baseline | 展示自然语言全文广播在最坏情况下的 token 膨胀 | 否，放附录或压力测试 |
| `baseline_bounded_nl_framework` | 有界自然语言多 Agent 框架 baseline | 模拟 AutoGen / LangGraph / CrewAI 中更常见的 bounded context 工程实践 | 是，主对照 |
| `runtime_lite` | 本系统低开销运行时 | SHP + state_ref + memory_ref + PromptView / MemoryView | 是，主方法 |

说明：

- 旧的 `baseline_text` 在 v5.10 后只作为兼容别名保留，语义等同于 `baseline_stress_full_broadcast`。
- 正式报告主表应比较 `baseline_bounded_nl_framework` 和 `runtime_lite`。
- `baseline_stress_full_broadcast` 保留价值，但不再用它单独支撑 “token 降低 90%+” 的主结论。

## 3. `baseline_stress_full_broadcast` 定义

该 baseline 模拟全历史自然语言广播：

```text
A2 携带 A1 的全部 Agent 发言；
A3 携带 A1+A2 的全部 Agent 发言；
后续任务继续累计；
B 组如果与 A 组在同一 runtime 中连续运行，也会看到前序自然语言历史。
```

该模式对应主流框架中未做上下文治理、或 AutoGen group chat 被不加约束地跨任务 resume 的最坏情况。

它的用途是说明：

- 全文广播协作会导致上下文膨胀；
- `runtime_lite` 在压力场景下有明显收益；
- 但它不代表普通开发者合理使用主流框架时的唯一基线。

## 4. `baseline_bounded_nl_framework` 正式定义

`baseline_bounded_nl_framework` 是一个主流多 Agent 框架近似 baseline，用于模拟不引入本系统运行时机制时，开发者在 AutoGen / LangGraph / CrewAI 等框架中常见的 bounded context 实践：

```text
任务内部使用自然语言共享上下文；
跨任务只传递最终交付物、最终交付物摘要和少量显式关键消息；
超过上下文预算后通过摘要压缩控制长度；
不使用 SHP、state_ref、memory_ref、PromptView、MemoryView、生命周期记忆、结构化状态池等本系统机制。
```

### 4.1 Thread 边界

规则：

```text
A 组和 B 组使用独立 conversation thread。
不同任务组之间不共享自然语言历史、运行中间状态或内部 Agent 发言。
只有 benchmark runner 的全局指标系统共享，不共享任务内容。
```

当前仓库中的 A/B 任务组为：

- A 组：旅行规划连续任务；
- B 组：安全审计连续任务。

外部评价中把 B 组称为“电商评论分析”，这与当前仓库不一致，不采用。

### 4.2 单任务内部上下文

规则：

```text
在单个 task / round 内，Planner / Retriever / Writer / Reviewer / MemoryManager 可以通过自然语言共享当前任务局部上下文。
该局部上下文仅在当前 task / round 内有效。
下一 task / round 不继承上一轮全部内部 Agent 对话。
```

举例：

```text
A3 内部的 Planner / Writer / Reviewer 可以共享 A3 的局部对话；
A4 不继承 A3 内部全部 Agent 发言；
A4 只继承 A3 的 accepted final output、bounded summary 和显式标记的 key messages。
```

### 4.3 跨任务传递内容

跨 task / round 只允许传递：

1. 上一轮 `accepted final output`；
2. 上一轮 `final output` 的 bounded summary；
3. 最近 `K` 条 explicitly marked key messages；
4. runner 级任务元数据，例如 `task_id`、`group_id`、`title`。

不允许传递：

1. Agent scratchpad；
2. 内部推理草稿；
3. 完整工具日志；
4. 完整中间 artifact；
5. 本系统的 state_ref / memory_ref / PromptView / MemoryView；
6. 状态池、记忆池、生命周期治理结果。

核心原则：

```text
baseline_bounded_nl_framework 只能使用普通框架中用户可见或开发者显式保留的自然语言交付物；
不能偷用本系统的结构化运行时状态。
```

### 4.4 固定参数

v5.10 默认实验参数固定为：

```text
local_round_context_budget = 8000 tokens
cross_round_context_budget = 1200 tokens
recent_key_messages_k = 2
summary_max_tokens = 500
```

含义：

- `local_round_context_budget`：单个 task / round 内部自然语言共享上下文预算。
- `cross_round_context_budget`：跨 task / round 传递给下一任务的自然语言上下文预算。
- `recent_key_messages_k`：允许跨任务携带的最近显式关键消息数量。
- `summary_max_tokens`：单个 bounded summary 的最大 token 数。

所有正式实验必须使用同一组参数。若后续做消融实验，可单独报告为 ablation，不混入主结果。

### 4.5 摘要成本计入 baseline

当 baseline 使用摘要压缩时，摘要生成本身的成本必须计入 baseline 总成本。

新增指标：

```text
summary_update_prompt_tokens
summary_update_completion_tokens
summary_update_total_tokens
summary_update_count
```

如果摘要由 LLM 生成，则使用 Provider usage 记录摘要 prompt / completion / total token。

如果摘要由确定性规则生成，也必须记录：

```text
summary_update_estimated_tokens
summary_update_method = deterministic
```

正式实验优先使用 LLM 摘要，以更贴近 CrewAI 自动摘要和普通框架工程实践。

## 5. Token 统计口径

v5.10 起，正式报告分清主指标和诊断指标。

### 5.1 主指标：Provider Usage

主表使用 Provider 返回的 usage 作为 LLM token 权威来源：

```text
provider_prompt_tokens
provider_completion_tokens
provider_total_tokens
```

其中：

```text
provider_total_tokens =
  provider_prompt_tokens
+ provider_completion_tokens
```

摘要生成、质量修复、重试等只要调用 LLM，都计入对应模式的 provider token。

### 5.2 诊断指标：tiktoken 估算

tiktoken 只用于估算非 Provider usage 直接给出的通信对象和可见上下文对象，例如：

```text
inter_agent_message_tokens_estimated
shp_packet_tokens_estimated
prompt_view_tokens_estimated
memory_view_tokens_estimated
state_view_tokens_estimated
artifact_digest_tokens_estimated
summary_text_tokens_estimated
```

注意：

```text
不能 baseline 用 tiktoken、runtime 用 provider usage。
不能把 provider prompt token 和同一段 prompt 的 tiktoken 估算重复相加后当作主成本。
```

正式报告建议：

- 主结论使用 `provider_total_tokens`；
- 机制拆解图使用 tiktoken 估算指标；
- 原 `end_to_end_collaboration_tokens` 改名或解释为 `collaboration_context_tokens_estimated`，避免和 provider usage 混淆。

## 6. 最终交付物口径

v5.10 必须拆分最终输出角色：

| 字段 | 中文说明 | 用途 |
|---|---|---|
| `draft_answer` | Writer 初稿 | 记录生成过程 |
| `review_report` | Reviewer 审查报告 | 质量门禁与审计证据 |
| `final_answer` | 最终对外交付物 | 质量裁判唯一对象 |

质量裁判只比较同一任务、同一交付类型的 `final_answer`。

规则：

```text
A10 final_answer = 最终旅行手册与决策日志正文。
B10 final_answer = 最终安全审计手册与系统决策日志正文。
Reviewer 审查报告保留为 review_report，但不作为 final_answer 直接参加主质量裁判。
```

## 7. 质量指标

只看 token 不够。v5.10 报告必须同时给质量指标。

通用指标：

```text
final_answer_present_count
final_answer_schema_complete_count
constraint_violation_count
llm_judge_score
llm_judge_winner
```

A 组旅行规划可检查：

```text
travel_days_valid
budget_valid
activity_intensity_valid
weather_backup_present
decision_log_present
gift_budget_present
```

B 组安全审计可检查：

```text
chain_graph_present
evidence_table_present
risk_priority_present
deprecated_clue_handled
decision_log_present
remediation_plan_present
```

正式结论应写成：

```text
baseline_bounded_nl_framework 能通过摘要压缩降低部分 token，但可能带来细节丢失；
runtime_lite 在较低 token 下仍可通过 state_ref / memory_ref 精确读取必要信息，因此质量更稳定。
```

如果实测不是这样，也必须如实报告。

## 8. v5.10 实施步骤

1. 扩展 `Mode`：
   - `baseline_stress_full_broadcast`
   - `baseline_bounded_nl_framework`
   - 保留 `baseline_text` 兼容别名。
2. 增加 bounded baseline 的上下文构造器：
   - task 内自然语言共享；
   - task 间仅 accepted final output / summary / K 条 key messages。
3. 增加 summary updater：
   - 记录 summary 生成 token；
   - 超过预算时压缩跨任务上下文。
4. 修改 deliverables：
   - 持久化 `draft_answer`、`review_report`、`final_answer`。
5. 修改质量裁判：
   - 只读取 `final_answer`；
   - 不因 token、协议结构或运行时机制加分。
6. 重新跑三列实验：

```powershell
F:\software\anaconda\envs\multi-agent-demo\python.exe -u examples\run_cross_task_eval.py --suite A --suite B --rounds 1 --mode baseline_stress_full_broadcast
F:\software\anaconda\envs\multi-agent-demo\python.exe -u examples\run_cross_task_eval.py --suite A --suite B --rounds 1 --mode baseline_bounded_nl_framework
F:\software\anaconda\envs\multi-agent-demo\python.exe -u examples\run_cross_task_eval.py --suite A --suite B --rounds 1 --mode runtime_lite
```

最终主表使用：

```text
baseline_bounded_nl_framework vs runtime_lite
```

压力测试附录使用：

```text
baseline_stress_full_broadcast vs runtime_lite
```

## 9. 当前决策

采纳：

1. 三层实验对象；
2. 正式名称 `baseline_bounded_nl_framework`；
3. thread 边界；
4. task 内共享、task 间有界传递；
5. 固定 K 和 context budget；
6. 摘要生成 token 计入 baseline；
7. Provider usage 作为主 token 指标；
8. `final_answer` 作为质量裁判唯一对象。

不采纳或修正：

1. 不采用“B 组是电商评论分析”的表述，当前 B 组仍是安全审计；
2. 不把 `baseline_stress_full_broadcast` 删除，它仍作为压力测试保留；
3. 不继续把旧 `end_to_end_collaboration_tokens` 当作唯一主成本指标，后续需改为主指标和诊断指标分离。

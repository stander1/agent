# v5.15n Provenance-Bound Historical Field Expansion

## Evidence

The v5.15m atomic-fact change prevents values, types, units, and audit
confidence from being separated during role-view selection. It also treats a
historical value repeated in the current task as direct task evidence.

That boundary does not cover a different valid request: the user can ask for
the current and former states without restating the former value. The value
must then be fetched from the admitted MemoryView. Broadcasting all historical
claims by default would restore stale-value contamination, so this requires a
separate, narrow expansion path.

## Generic Invariants

### Explicit temporal intent

Historical facts are fetched only when the current task contains all three
signals:

- a generic current-state reference;
- a generic historical-state reference;
- a generic instruction to preserve, compare, list, label, or otherwise
  produce the paired states.

A task that merely mentions an old discussion while requesting only the
current result does not qualify.

### Provenance-bound expansion

Expansion reads only resolved `ccf.v2` MemoryViews already selected for the
receiver. It returns complete typed `historical_fact` JSON records and never
re-parses free text to invent a former value. Audit confidence remains outside
the model-facing view.

The expansion is charged to the existing field-fetch counters and token
ledger. It is therefore visible in end-to-end collaboration cost rather than
being treated as free context.

### Output authorization

A historical value is not automatically safe merely because it was fetched.
The memory-adoption guard authorizes it only when:

- the current task requests the paired current and historical view;
- the output also contains the active fact from the same semantic slot;
- the output locally labels the former value as historical.

An unlabeled former value, a current-only request, or a historical value from
a different slot remains unsafe and is repaired or blocked by the existing
guard.

## Scope

The implementation uses temporal status, semantic identity, typed values,
MemoryView provenance, and local output evidence. It does not depend on
Question A/B, fixed Agent roles, particular domains, values, units, or
field-name dictionaries. Existing domain parsers remain optional candidate
providers and do not bypass memory admission.

## Acceptance Boundary

Regression coverage requires:

- paired temporal intent to be recognized independently of a business domain;
- current-only requests to reject historical expansion;
- historical prompt views to preserve whole typed records and omit confidence;
- field-fetch token accounting to include historical expansion;
- an unstated but requested former value to pass only alongside its active
  same-slot value and an explicit historical label;
- a former value from another slot to remain blocked;
- a post-commit external holdout to validate the full AutoGen path.

# v5.15m Typed Fact Atomicity and Task-Grounded History

## Evidence

The post-v5.15l geodetic holdout stored the correct active facts:

- a signed scalar remained an equality with positive logical polarity;
- boolean `false` remained an active boolean value;
- the revised scalar retained distinct active and superseded values.

The model-visible role view nevertheless split each fact into independently
ranked lines. The boolean fact lost its `active_value=false` line while an
adjacent fact retained `confidence=0.72`. Every receiving Agent then emitted
`0.72` as the boolean value. On the revision task, the current user request
provided both the current and archived values, but the memory-adoption guard
classified the archived value as stale memory and rewrote it to the active
value.

## Generic Invariants

### Atomic model facts

Each admitted `ccf.v2` fact is rendered as one compact JSON object:

```text
active_fact={"slot_id":"...","scope":"...","value":"...",
"value_type":"...","unit":"...","operator":"...","polarity":"...",
"status":"active"}
```

The role-view selector can retain or omit the whole fact, but cannot select a
predicate, type, value, or unit independently. Audit confidence is excluded
from model-facing facts and remains available in storage, audit views, traces,
and reports.

Revision policy is also an atomic JSON record. It contains the authoritative
active value and a generic current-versus-historical policy, but no historical
value is broadcast by default.

### Task-grounded historical values

A historical value that is present verbatim as the same typed fact in the
current user task is direct task evidence. The memory-adoption guard excludes
it from stale-memory attribution, just as it already excludes active facts
that are repeated in the current task.

This does not authorize arbitrary historical recall. A historical value that
is absent from the current task remains unsafe and continues to be repaired or
blocked. Fetching an unstated historical value requires a separate,
provenance-bound field expansion path.

## Scope

The implementation uses schema fields, value normalization, source text, and
revision status. It does not depend on Question A/B, a business domain,
specific values or units, or fixed Agent roles.

## Acceptance Boundary

Regression coverage requires:

- two unrelated typed facts to survive a constrained role-view budget as
  complete atomic records;
- model-facing facts to exclude audit confidence;
- a current task that explicitly provides active and archived values to pass
  without stale-memory repair;
- an old value absent from the current task to remain blocked;
- existing signed-scalar, boolean, revision, capability-view, and AutoGen
  memory tests to remain green.

A post-commit external holdout is still required before this mechanism is
treated as end-to-end validated.

# v5.15o Provenance-Bound Revision Admission

## Evidence

The post-commit v5.15n holdout passed its declared 16 checks, but its later
answer did not exercise historical MemoryView expansion. The new signed scalar
appeared in a task-level candidate and output while the admitted ClaimCard and
MemoryView still exposed the former scalar as active. Control disambiguation
accepted only one unchanged boolean and rejected the scalar candidates.

This is an admission failure before retrieval. A passing answer is therefore
not evidence that revision history is usable until the new fact reaches the
ClaimCard, the former fact becomes historical, and a later task fetches that
history without restating it.

## Generic Invariants

### Evidence-bound local span recovery

Exact unique source quotes remain the primary authority. When a control model
changes punctuation around an otherwise source-grounded claim, a candidate may
recover an exact local source span only when all of the following hold:

- the proposed literal value has one qualifying occurrence;
- the open predicate's lexical tokens occur in the same structural clause;
- the proposed unit, when present, occurs in that clause;
- the recovered clause is unique.

Missing values, repeated qualifying anchors, unsupported fields, or fabricated
relations remain rejected. The system records local recovery and partial
rejection diagnostics in typed validation and trace output.

JSON scalar conversion preserves `false` and `0`; these values must not collapse
to an empty string during candidate construction.

### Evidence-backed predecessor binding

A changed value never replaces an active claim merely because it is newer. The
candidate must first carry an explicit, source-validated `supersedes_value`
relation. If that relation names an admitted active value, it binds to that
claim. If it refers anonymously to a former value, binding is allowed only when
exactly one different active predecessor exists in the same semantic identity.
Ambiguous predecessor sets remain unresolved.

The resulting target is a candidate or claim identifier already present in the
store, so the existing conflict resolver remains responsible for moving the
former claim into MemoryView history.

## Scope

The implementation depends on exact source spans, open predicate tokens, typed
values, units, semantic identity, explicit revision relations, and active claim
cardinality. It does not depend on Question A/B, fixed agent roles, named
business fields, domain vocabularies, value-specific regular expressions, or
recency-only overwrite.

## Acceptance Boundary

Regression coverage requires:

- a punctuation-varied but uniquely grounded signed scalar to enter memory;
- JSON `false` and `0` to retain their literal values;
- fabricated and multiply anchored proposals to remain rejected;
- an explicit anonymous revision to bind only a unique active predecessor;
- the new fact to be active and the former fact historical in MemoryView;
- unchanged same-slot facts to deduplicate normally;
- local-recovery and partial-rejection diagnostics to be observable;
- a post-commit unseen-domain AutoGen holdout to fetch unstated history and
  charge it to the field-fetch and token ledgers.

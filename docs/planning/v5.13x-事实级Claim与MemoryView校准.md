# v5.13x：事实级 Claim 与 MemoryView 校准方案

## 1. 阶段定位

v5.13x 不新增第四套创新机制，也不针对 D1-D3 编写领域规则。

本阶段用于把当前工程重新校准到三份最终创新方案已经定义的 TLC-Memory 主线：

```text
Agent 输出 / 运行时状态
  ↓
Promotion View
  ↓
Memory Candidate + Claim Candidates
  ↓
Memory Admission Lite
  ↓
provisional_active Claim Cards
  ↓
Schema Registry 对齐
  ↓
Batch Compaction
  ↓
Deterministic Conflict Resolver
  ↓
MemoryView(active / historical / conflicting)
  ↓
角色最小 Prompt View
```

本阶段不修改 AutoGen 中的 Agent 名称、角色数量和业务提示词。动态能力画像继续决定角色视图，TLC-Memory 只负责事实、版本、冲突和视图。

## 2. 创新方案中的明确要求

### 2.1 Claim Card 是最小候选单元

《记忆生命周期管理v3》明确规定：

```text
Claim Card 是 TLC-Memory 中最小粒度的候选记忆单元；
整段 Agent 输出不能直接作为共享记忆；
混合输出必须拆成多个可比较、可归并、可追溯的 Claim Card。
```

因此，“整篇最终交付物等于一个 Claim”不符合最终方案。

### 2.2 Claim 必须采用 Canonical Claim Form

正式 Claim 至少需要：

```text
subject
slot_id
value
scope
temporal_scope
certainty
modality
polarity
source_agent
confidence
schema_version
```

冲突判断应回答：

```text
同一个 subject 的同一个 slot 是否发生值变化；
变化是否处于重叠 scope；
新旧 temporal_scope 是否重叠；
新值是否明确替代旧值。
```

不能根据两篇自然语言文档是否相似来决定版本冲突。

### 2.3 MemoryView 按语义键组织事实

Batch Compaction 应按以下组合分组：

```text
subject + slot_id + scope + temporal_scope
```

每个 MemoryView 必须提供：

```text
active_value
historical_values
conflicting_values
resolution_status
downstream_policy
```

如果冲突无法确定：

```text
resolution_status = unresolved_conflict
downstream_policy = do_not_use_for_final_generation
```

### 2.4 写入路径保持轻量

Memory Admission Lite 只负责低价值过滤、Claim 生成、Schema 对齐、基础去重、时间信息和 provisional 写入。

复杂冲突不应阻塞每次写入；应在任务阶段结束或积累一定数量 Claim 后，由 Batch Compaction 局部处理。只有高价值且规则无法判断的疑似冲突，才允许在预算内调用 LLM 或 Reviewer。

### 2.5 Prompt View 与 Audit View 必须分离

业务 Agent 默认只读取 active_value 和必要置信信息，不读取完整历史 Claim、lineage 和原始文档。

历史值、冲突证据和来源链只进入 Audit View。需要细节时再通过字段级接口渐进展开。

## 3. 当前实现与创新方案的差异

| 位置 | 当前实现 | 创新方案要求 | 影响 |
|---|---|---|---|
| Claim 粒度 | AutoGen 最终 summary 被写成一个 Claim | 混合输出拆成多个 Claim Card | 整篇旧文档被整体标记为 superseded |
| ClaimCandidate | 候选被记录，但准入后没有逐条转成正式 ClaimCard | admitted ClaimCandidate 应成为正式 ClaimCard | `claim_cards` 没有真正驱动 MemoryView |
| Claim 字段 | 有 subject、slot、value 等 lite 字段，但缺少独立 scope、certainty、valid_from/valid_to | 完整 CCF | 无法准确判断适用范围和时间重叠 |
| subject | 通常使用统一 task_topic | 应表示真实主体 | 同一协作组的不同事实容易被误合并 |
| MemoryView 键 | 只使用 `slot_id` 生成 view_id | `subject + slot_id + scope + temporal_scope` | 所有最终交付进入同一个大视图 |
| 通用 Slot | 最终交付统一进入 `slot.system.deliverable_requirement` | Slot 表示稳定语义字段 | 架构、并发、审计、RTO 被混成一个值 |
| 写入状态 | 准入后直接 active，并立即替代旧 Claim | 先 provisional_active，阶段结束再 Compaction | 写路径承担了不完整的冲突决策 |
| 冲突策略 | 所有 Slot 基本使用 confidence + latest | 每个 Slot 在 Registry 中配置策略 | 不同语义被同一规则处理 |
| unresolved conflict | 数据结构存在，但没有实际向 `conflicting_claim_ids` 写入的路径 | 无法解决时显式记录并阻断 Prompt | 当前 unresolved 冲突门禁没有完整生效 |
| Prompt View | 返回拼接后的整篇 `prompt_summary` | 默认只返回 active_value | Token 较大，也使归因依赖自然语言模糊匹配 |
| 采用归因 | 用全文片段、数字和相似度匹配 active/historical | 比较同一语义键的结构化值和极性 | 未变化旧事实被误判为 mixed |
| Batch Compaction | 主要过滤状态并拼接 summary | 分组、值归一、去重、冲突消解、lineage | 还不是真正的 TLC Batch Compaction |

## 4. v5.13w 误报的形成过程

当前路径：

```text
D1 整篇输出
  → slot.system.deliverable_requirement
  → Claim A

D2 整篇输出
  → 同一个 slot、同一个 task_topic
  → Claim B 替代整个 Claim A
  → Claim A 全文进入 historical

D3 继续使用仍然有效的“SQLite WAL + 文件载荷”
  → 与 Claim A 中相同描述发生文本匹配
  → 分类器认为输出同时使用 active 和 historical
  → mixed
```

正确路径应当是：

```text
D1:
architecture = sqlite_wal_file_payload
peak_concurrency = 20
external_services_allowed = false

D2:
architecture = sqlite_wal_file_payload
peak_concurrency = 50
audit_retention_days = 7
write_model = single_writer_queue

Compaction:
architecture：相同值，合并证据，不产生历史冲突
peak_concurrency：20 → 50，20 进入 historical
audit_retention_days：新增 active
write_model：新增 active
```

D3 使用 `architecture=sqlite_wal_file_payload` 应判为 useful；只有 D3 重新使用 `peak_concurrency=20` 时才应判为 wrong。

## 6. Claim 获取策略

AgentLite 面向任意 AutoGen Agent，不能要求开发者必须使用固定角色，也不能假设所有 Agent 都会输出标准控制头。

Claim 获取按以下优先级进行：

### 6.1 第一优先级：已有结构化 Claim

如果 Agent Output Contract 已提供 `claim_cards`，直接进行 Schema 校验和 CCF 标准化。

### 6.2 第二优先级：结构化状态和产物

从以下机器可读字段生成 Claim：

```text
JSON / YAML 字段
工具返回值
状态对象的结构化 metadata
显式 key-value
表格中的字段和值
```

### 6.3 第三优先级：规则优先的自然语言提取

只提取高置信的显式事实：

```text
明确选择：选择/采用/保持 X
明确约束：禁止/必须/不得 X
显式数值：并发=50、保留=7天、RTO<15秒
显式修订：从 X 改为 Y、提高到 Y、取消 X
```

提取器只识别通用语义形态，不包含旅游、系统部署或 Question D 的专用词表。

### 6.4 第四优先级：低频语义兜底

规则无法提取、但候选重要性高且会被多 Agent 复用时：

```text
进入 pending
  ↓
使用短上下文 Claim Extractor 或 Reviewer
  ↓
输出受 CCF Schema 约束的 Claim Cards
  ↓
再次执行规则校验
```

该调用受 `control_llm_tokens` 和候选数量预算限制，不在每条消息上执行。

### 6.5 禁止的 fallback

如果无法提取结构化 Claim：

```text
完整输出保留为 Promotion View / Audit Artifact；
候选保持 pending 或 audit_only；
不得再把整篇 summary 作为 final_deliverable Claim 写入正式 MemoryView。
```

## 7. Schema RegistryV2

Registry 继续使用有限、稳定的核心 Slot：

```text
slot.user.preference
slot.project.requirement
slot.project.state
slot.system.design_decision
slot.system.failure_pattern
slot.system.reuse_strategy
slot.runtime.config
slot.tool.result
slot.paper.evidence
```

每个 Slot 定义：

```text
value_type
scope_required
temporal
aliases
allowed_modalities
conflict_policy
prompt_visibility
```

具体语义字段放入规范化 `scope`，例如：

```text
constraint.peak_concurrency
constraint.audit_retention_days
constraint.recovery_rto
architecture.storage
runtime.write_model
```

无法映射的内容进入 `unresolved_slot` 或 `unresolved_scope` 队列，不进入正式 Prompt View。Schema 提案可以半自动生成，但正式注册必须通过确定性校验。

## 8. Batch CompactionV2

Compaction 在 Team 最终任务完成后或 Claim 数量达到阈值时执行：

```text
收集 provisional_active Claims
  ↓
按 subject / slot_id / scope / temporal_scope 分组
  ↓
按 value_type 规范化值和单位
  ↓
相同值合并 supported_by
  ↓
应用 Slot conflict_policy
  ↓
生成 active / historical / conflicting
  ↓
Schema-Constrained Validation
  ↓
写入 MemoryViewV2、lineage 和 compaction_log
```

确定性规则：

1. 语义键不同：不是冲突。
2. 同键同值：合并证据，不产生 superseded。
3. 同键不同值且存在显式修订：新值 active，旧值 superseded。
4. 同键不同值但 scope 或时间不重叠：按时间线并存。
5. 同键不同值且无法决定：写入 conflicting_values，禁止进入最终 Prompt。

## 9. Prompt、Guard 与渐进展开

### 9.1 业务 Prompt View

默认只返回：

```json
{
  "semantic_key": "project:current|slot.project.requirement|constraint.peak_concurrency",
  "active_value": 50,
  "unit": "task",
  "status": "active"
}
```

动态能力画像继续决定某个 Agent 需要哪些语义键。这里不固定 Planner、Writer、Reviewer。

### 9.2 Revision Guard

只有某个语义键确实发生值替代时才生成：

```text
[revision_guard]
constraint.peak_concurrency 的当前有效值为 50；
只使用 active_value；
框架历史中的旧值不得作为当前结论。
```

业务 Prompt 不注入旧值全文。历史 Claim 和冲突比较只留在 Audit View。

### 9.3 字段级补取

Agent 缺少细节时调用：

```text
get_prompt_view(semantic_keys)
expand_evidence(view_id, row_id)
get_audit_view(view_id)
```

避免一次展开完整历史文档。

## 10. useful / wrong / mixed 的新判定

对 Agent 输出使用同一套 Claim 提取和 CCF 标准化，再与注入的 MemoryView 比较。

### useful

输出采用 active_value，没有肯定采用互斥 historical_value。

### wrong

输出肯定采用已经被替代的 historical_value，且没有采用 active_value。

### mixed

输出同时肯定采用同一语义键下互斥的新旧值。

### unassessed

输出无法提取对应语义键，或证据不足。

仅有文本相似、共用数字、共用 evidence_id、提及旧值但明确否定，都不能判为 wrong 或 mixed。

每个判定必须记录：

```text
semantic_key
active_value
historical_value
matched_output_span
polarity
classification_reason
```

### 11.2 旧快照迁移


## 13. 验收标准

### 13.1 确定性单元验收

至少覆盖：

1. 同一事实重复出现，只合并证据。
2. 同 Slot 不同 scope，不冲突。
3. 同 scope 不同 subject，不冲突。
4. 数值 20 修订为 50，20 进入 historical。
5. 输出采用 50，判 useful。
6. 输出采用 20，判 wrong。
7. 输出同时采用 20 和 50，判 mixed。
8. 输出提及“不要使用 20”，不得判 wrong。
9. 无法映射 Slot/Scope，不进入 Prompt View。
10. unresolved conflict 不进入最终生成。
11. 角色视图不膨胀。
12. legacy document claim 不参与负向污染计数。

### 13.2 通用性验收

使用至少两个不同领域的连续任务链，不修改运行时代码：

```text
系统配置修订链；
普通规划约束修订链。
```

验证同一事实继承、明确修订、否定旧值和不相关数字不会被混淆。

### 13.3 真实 AutoGen 验收

- Agent 名称继续使用任意名称。
- Native、Observed、Managed 使用相同 Team 和调用上限。
- Managed 保持前序 active_value。
- 历史值不直接进入业务 Prompt。
- 事实级分类人工抽查无假阳性。
- Provider Token 和端到端协作 Token 分别统计。
- 质量盲评不得相对 Native 显著下降。

## 14. 实施顺序

v5.13x 作为一个正式版本完成，不再拆成对外的小版本。内部按以下顺序提交和验证：

```text
阶段 A：ClaimCardV2、MemoryViewV2、Schema RegistryV2 和兼容加载
阶段 B：Claim Capture、逐条准入和 Batch CompactionV2
阶段 C：事实级 Prompt View、Revision Guard 和采用归因
阶段 D：指标、监控、迁移、确定性验收和真实 AutoGen 实验
```

每个阶段都保持测试可运行，但只有 A-D 全部完成后才标记 v5.13x 完成。

## 15. 明确不做的修改

```text
不固定 Planner / Writer / Reviewer；
不添加 Question A、Question D 或旅游/部署专用规则；
不通过增加 Agent 轮次掩盖记忆错误；
不把完整历史广播给所有 Agent；
不把每条消息都交给额外 LLM 做 Claim 提取；
不删除旧原始 Claim 和审计证据；
不把 unresolved conflict 强行选成 active_value；
不把 Token 降低作为覆盖语义必要性的唯一门禁。
```

## 16. 阶段完成定义

只有同时满足以下条件，v5.13x 才算完成：

```text
整篇最终交付不再作为单一正式 Claim；
admitted claim_cards 真正逐条进入 ClaimCard；
MemoryView 使用复合语义键；
同值继承不会产生 historical 冲突；
明确修订能够产生 active / historical；
无法解决的冲突被阻断；
Prompt 只暴露 active_value；
useful / wrong / mixed 可提供字段级证据；
跨领域验收无领域专用代码；
端到端成本和质量仍保持可接受。
```

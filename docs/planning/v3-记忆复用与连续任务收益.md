# v3：记忆复用与连续任务收益

## 1. 版本定位

v3 的目标是让系统真正体现连续任务收益。

本版本重点不是继续缩短单条消息，而是证明：

```text
第一轮任务产生的状态和记忆，可以在后续相关任务中被复用；
系统因此减少重复检索、重复总结和重复上下文输入。
```

## 2. CMJCC-v3

新增：

```text
Communication Gate:
  判断是否需要交接、交接给谁、是否只发引用。

Memory Admission Gate:
  根据 confidence、importance、reuse_scope 决定是否进入记忆候选。

Memory Access Controller-lite:
  默认读取 Prompt View，必要时展开 evidence snippets。

Context-Pruned Retry-lite:
  当控制头规则修复失败时，不继承完整 Artifact 上下文，只用坏控制头、schema error、artifact_digest 和目标 schema 进行一次短上下文格式重试。
```

Context-Pruned Retry-lite 的边界：

```text
不重新执行任务；
不重写 Artifact；
不读取完整长正文；
只修复 <CMJCC_CONTROL>；
每个 Agent 输出最多重试 1 次；
失败后进入 fallback wrapper 并记录 contract_violation。
```

该机制必须在 v3 前调，因为连续任务复用依赖稳定的结构化输出。如果第 7 轮控制头崩溃，系统不能因为 JSON 问题直接中断整条流水线。

## 3. SHP-State-v3

新增 State-to-Memory 简化桥：

```text
Runtime State
  ↓
Promotion View
  ↓
Claim Card
  ↓
MemoryView
```

例如 retrieval_state 晋升为：

```json
{
  "promotion_view_id": "pv_001",
  "source_state_id": "state_retrieval_001",
  "core_claim": "结构化协议能降低直接文本通信，但需要统计记忆读取成本。",
  "evidence_refs": ["chunk_001", "chunk_004"],
  "reuse_intent": "后续分析多 Agent 通信成本时复用"
}
```

## 4. TLC-Memory-v3

新增：

```text
Claim Card
Schema Registry 简化版
MemoryView
Batch Compaction 简化版
Prompt View / Audit View 分离
```

Schema Registry 先限制在少量 slot：

```text
slot.system.optimization_claim
slot.user.preference.programming_language
slot.project.implementation_language
slot.runtime.execution_language
slot.system.design_decision
slot.system.failure_pattern
slot.system.reuse_strategy
slot.paper.evidence
slot.project.requirement
```

同时引入静态 Alias Mapping Dict，优先用规则做 slot 对齐：

```json
{
  "coding_lang": "slot.runtime.execution_language",
  "runtime_language": "slot.runtime.execution_language",
  "programming_language": "slot.project.implementation_language",
  "implementation_language": "slot.project.implementation_language",
  "user_favorite_language": "slot.user.preference.programming_language",
  "preferred_programming_language": "slot.user.preference.programming_language",
  "failure_reason": "slot.system.failure_pattern",
  "error_pattern": "slot.system.failure_pattern",
  "reuse_hint": "slot.system.reuse_strategy",
  "reuse_strategy": "slot.system.reuse_strategy"
}
```

Slot 对齐顺序：

```text
1. 标准 slot_id 精确匹配；
2. alias 字典匹配；
3. 字符串归一化后匹配；
4. 编辑距离 / token overlap 规则兜底；
5. 仍失败则进入 unresolved_slot，不进入普通 Prompt View。
```

v3 不默认调用 LLM 做 slot 对齐，避免记忆治理本身制造额外 token 成本。

注意：Alias Mapping 不能过粗。`用户偏好语言`、`项目实现语言`、`运行时执行语言`、`系统设计决策` 必须分开建 slot，避免把“用户会 Python”“项目使用 Rust”“沙箱执行 Python”误合并到同一个 MemoryView。

MemoryView 原则：

```text
不创造新事实，只组织 Claim。
```

记忆检索后端：

```text
keyword / tag:
  SQLite LIKE、FTS 或倒排索引。

semantic similarity:
  轻量向量索引，优先本地 cosine / FAISS / Chroma 三选一。

fallback:
  无向量库时使用 TF-IDF 或 keyword score，但实验报告需标注 retrieval_backend。
```

## 5. 连续任务实验

任务组 A：

```text
A1 分析低开销通信；
A2 分析非文本状态传递，并复用 A1；
A3 分析共享记忆机制，并复用 A1/A2。
```

任务组 B：

```text
B1 检索材料；
B2 执行代码分析；
B3 基于 B1/B2 生成报告并复用失败经验。
```

## 7. 验收标准

```text
1. 第一轮任务能产生 Claim Card 和 MemoryView；
2. 后续相关任务能命中 MemoryView；
3. Agent 默认只读取 Prompt View；
4. Reviewer 可以展开 Audit View；
5. 与无记忆模式相比，重复检索或重复总结下降；
6. 能解释每次记忆命中的来源和作用；
7. 控制头规则修复失败时，能通过短上下文重试恢复至少一类常见格式错误；
8. Schema Registry 具备静态 alias 映射，避免同义 slot 膨胀；
9. 能区分 memory_hit 和 useful_memory_hit，避免把无效命中当作复用收益。
```
